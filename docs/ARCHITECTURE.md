# telegram-feed — Architecture

Companion to [SPEC.md](SPEC.md).

## 1. Summary

- **Flutter** app, Android only.
- **TDLib**, Telegram's client library, through its JSON interface (`td_json_client`) via `dart:ffi`.
- The TDLib client and the rule engine live in one **core isolate**. With background watching on, a foreground service hosts it, so it keeps running when the UI is closed. With background watching off, the UI spawns it. The UI is a client of the core.
- Data TDLib does not own (feeds, sources, rules, settings) lives in **SQLite** through **Drift**. Read state is Telegram's own and stays in TDLib.
- No backend. The device talks to Telegram, and, when the user turns them on, to the user's own Google Drive (sync) and to an AI endpoint the user configures (AI rules).

```
┌─────────────────────────────── device ───────────────────────────────┐
│  UI isolate (Flutter)                                                │
│   screens ── FeedTimeline / FeedSearch ── CoreClient ── AppDatabase  │
│                                              │                       │
│  ─────────────────────────────────────────── │ ───────────────────── │
│  Service host (root isolate of the foreground service's engine)      │
│   CoreServiceHandler ── Notifier ── TtsService ── SemanticGate       │
│                                              │                       │
│  ─────────────────────────────────────────── │ ───────────────────── │
│  Core isolate                                                        │
│   CoreServer ── TdlibGateway ── RuleEngine ── AppDatabase            │
│                     │                                                │
│   TDLib (td_json_client via FFI)                                     │
└──────────────────────────────────────────────────────────────────────┘
```

## 2. Technology choices

| Choice | Reason |
|---|---|
| TDLib | Handles auth, updates, media download and a local message cache. The Bot API cannot read arbitrary channels. |
| Session on the device | No server and no custody of user sessions. Real-time notifications need the app to stay alive, which a foreground service provides on Android. |
| Flutter | Mature FFI and one codebase. |
| Core isolate separate from the UI | The UI can be destroyed while the service keeps the core running. TDLib stays in Dart, with no Kotlin implementation. |
| Drift (SQLite) | Relational data (feeds ↔ channels, rules) with real queries. |
| Device TTS via `flutter_tts` | Free, offline, works with the screen off. |

## 4. Telegram gateway

`TelegramGateway` is the only layer that knows about TDLib. Everything above it works with app-level types (`Channel`, `Post`, `Media`, `Comment`, `FileRef`).

| Area | Members |
|---|---|
| Login | `authState`, `setPhoneNumber`, `checkCode`, `resendCode`, `setEmailAddress`, `checkEmailCode`, `checkPassword`, `registerUser`, `requestQrCode`, `logOut`. An authorization state the app has no step for (a Premium purchase) is `AuthUnsupported`, which the login shows as a screen of its own |
| Channels | `myChannels`, `membershipEvents`, `chatFolders`, `archivedChannels`, `savedMessages`, `channelInfo`, `similarChannels`, `pinnedPosts`, `mediaCalendar`, `mapThumbnail` |
| Posts | `history`, `historyAfter`, `postEvents`, `markViewed`, `countViews`, `readState`, `readUpdates`, `messageIdByDate`, `customEmoji` |
| Search | `searchHistory`, `searchAllChannels`, `searchThread`, `mediaCounts` |
| Files | `download`, `fileProgress`, `downloadFrom`, `downloadedPrefix`, `cancelDownload` |
| Interactions | `availableReactions`, `react`, `markChannelUnread`, `saveToSavedMessages`, `deleteFromSavedMessages`, `report`, `discussion`, `threadHistory`, `threadAround`, `markCommentsViewed`, `reply`, `editComment`, `deleteComments`, `retryComment`, `comments`, `commentsGone`, `closeThread` |
| Account and state | `me`, `storageStats`, `storageByKind`, `clearCache`, `setCacheLimits`, `connection`, `close`. `clearCache` calls `optimizeStorage` with every limit at 0 and every file type named: with TDLib's default limits (-1) only files unused for weeks go, and with no types named thumbnails, profile photos, stickers and wallpapers stay, so the cache would not shrink to what `getStorageStatisticsFast` counted. Given kinds, it names only their file types |

Implementation:

- `TdlibGateway` (package `telegram_gateway`) runs over a `TdTransport` (raw JSON in, raw JSON out). `TdClient` matches responses to requests by `@extra`, decodes updates with `tdlib_bindings` and hands them to the gateway strictly in order, so an edit that needs a `getMessage` round trip cannot be overtaken by the following delete.
- `FfiTransport` loads `libtdjson`, polls `td_receive` in one long-lived receive isolate and demultiplexes by `@client_id`. TDLib aborts the process if `td_receive` is called from two threads, so there is exactly one receive isolate per process. Imported from `package:telegram_gateway/tdlib_ffi.dart`.
- Post events are emitted only for chats known to be channels. `updateMessageContent` and `updateMessageEdited` are re-fetched with `getMessage`, so `PostEdited` carries the full post. `updateDeleteMessages` is forwarded only when `is_permanent`.
- TDLib answers `getChatHistory` with short pages, often a single cached message. `history` pages until the limit or the end. Local reads (`only_local`) stay a single probe.

TDLib parameters: `use_message_database`, `use_chat_info_database` and `use_file_database` are true; the files directory is `files/` inside the account's TDLib directory. TDLib owns message and file caching; the app never copies message bodies into its own database.

API credentials: `api_id` and `api_hash` come from `--dart-define=TG_API_ID=... --dart-define=TG_API_HASH=...`. The repository contains none. CI injects them from secrets.

## 5. Feeds

### 5.1 Data model (Drift, schema version 7)

```
feeds            (id, name, position, created_at, sync_id, updated_at, filter_json?)
feed_sources     (feed_id, chat_id, position, added_at)                 -- PK (feed_id, chat_id)
watched_channels (chat_id, title, username?)
rules            (see section 6.1)
settings         (key, value, updated_at?)
sync_tombstones  (kind, sync_id, deleted_at)                            -- PK (kind, sync_id)
```

`watched_channels` is the union of all feed sources: every channel the app watches.

The UI, the background service and the core each open their own connection to the file (`appDatabaseFile`). Every connection sets `busy_timeout` to five seconds, so a write waits for another connection's write instead of failing with "database is locked".

After an update all three connections find the old schema at once, and drift runs a migration outside any transaction. `AppDatabase._migrate` therefore takes the whole migration into one `BEGIN EXCLUSIVE` transaction, reads `user_version` again inside it and stamps the new one there: the connection that arrives second waits (`busy_timeout` is a minute while migrating) and then finds nothing left to do, instead of working on a schema another connection is replacing.

### 5.2 Sources

Only channels the account has joined can be added. The picker lists `myChannels()` with a search box; several channels are ticked and added with one press. A checkbox under the search, shown when some channel is in a feed already, leaves those channels out (`picker.hideInFeeds`, kept on the device) and unticks the ones it hides. The app never calls `joinChat`, `leaveChat` or `searchPublicChat`, and never changes Telegram-side mute or folder settings. Every source is a joined chat, so TDLib delivers `updateNewMessage` for all of them and nothing is polled.

When the user leaves a channel in the official app, `membershipEvents` reports it. The source stays in its feeds, marked as left, until the user removes it.

### 5.3 Merged timeline

The timeline is a k-way merge over per-channel histories, ordered by `(date desc, chat_id, message_id desc)`.

- `FeedTimeline` keeps one cursor per source (`oldestLoadedMessageId`) and a small page buffer.
- Loading a page: every source whose buffer is empty fetches its next `history()` page (limit 30), all at once. Then rows are popped from a max-heap keyed by date until the page is full. A source that returns nothing is exhausted.
- Live updates: `postEvents` for any source are inserted at the newest end when the reader is there; otherwise they wait and are counted on the button to the newest posts, which releases them.
- Layout: the list is reversed (index 0 is the newest post, at the bottom), so loading older pages appends at the far end and never shifts what is on screen. A row inserted at the newest end shifts every index; the screen then re-anchors on index 0. Rows are keyed by `(chat_id, album or message id)`.
- Opening (`_open` in `TimelineScreen`), as the official app opens a chat: the list widget takes its start position only when it is first built, so the first pages load before it is. The position is, in this order: the post a notification asked for; where the reader left the timeline scrolled up; the first unread post; the newest post. For the first unread post the sources load down to Telegram's read positions, at most 300 rows. When Telegram counts more unread posts than that (the sum of `ReadState.unreadCount`, taken at its word only in a timeline without a filter), or the 300 rows end before the read positions, the timeline is rebuilt around its oldest unread post instead, as the official app loads a chat around its first unread message (`_reopenAtOldestUnread`): `historyAfter(mark, limit: 1)` tells each source's first unread post, the earliest of them anchors its own channel and `anchorsForDate` the others, one page of newer posts loads, and the opening goes on as below. The button to the newest posts then shows Telegram's count until the rows up to the newest post are loaded. The "Unread posts" divider is drawn on top of that row, and the row above it is aligned just below the top of the screen, or just below the pinned bar where a channel shows one (`_underTop`; the opening waits up to two seconds for the pinned posts, which load beside the first page). When the unread posts do not fill the screen, the newest post goes to the bottom instead of leaving a gap.
- The kept position (`SavedPosition`, `feeds/saved_position.dart`) is the lowest row on the screen and the height of its bottom edge, in the settings under `position.feed.<id>` or `position.chat.<chat id>`, on this device only. It is written when the timeline closes and when the app pauses, and removed instead when the reader is at the newest post or that row is still unread, as the official app does. Opening searches it among the newest 300 rows; everything newer than it is loaded on the way, so the divider goes on the first unread post below it. A rebuild within the visit (a changed filter or source) keeps the reader where they are.
- The divider belongs to the visit: it keeps its row through jumps and rebuilds, and the timeline notes when it has been on the screen.
- A rebuild of a list that stays up (the loading spinner in between may never be drawn) jumps to its opening position after the frame; the positions reported until that jump is laid out describe the old list and are ignored.
- Album messages (`media_album_id`) collapse into one row.
- Edits replace a row in place; deletes remove it.
- Rebuilds touch only the rows that changed. `TimelineScreen` keeps the widget it built for each row with what it was built from (`_RowInputs`: the item and its posts by identity, the channel's title, photo and info, the reader's pending reactions, selection, highlight, day pill and divider) and hands the same widget back while those stay the same, so an edit (TDLib reports view counts of the posts on the screen as edits), a page of older posts or a reaction builds one row, not the screen. Reading while scrolling and posts held behind the button change only the button at the corner, which listens on its own notifier. Posts of channels outside the timeline change nothing.

The timeline persists nothing. TDLib's local message database answers a history request in about 2 ms.

### 5.4 Read state

Read state works as in the official Android app (`ChatActivity` in its source), with a feed read like one chat.

- The read state is Telegram's own: one read position per channel (`last_read_inbox_message_id`), shared by every feed that holds the channel, the channel's own timeline and the official app. The app stores none. `readState(chat)` reads it with the unread count and the newest post (TDLib's `getChat`); `readUpdates` carries TDLib's `updateChatReadInbox`, which comes whenever a position moves (here, in the official app, on another device) or the unread count changes. The timeline keeps the positions of its channels in memory from there and moves them as the reader reads.
- A post is read once 80 % of its row has been above the bottom edge of the screen, an album's row once all of it has (`visibleToBeRead` of the official app). Of the rows that pass, the newest decides: `FeedTimeline.passedAt` names, for every channel of the timeline, its newest post at that row or older in the timeline's order (shown or hidden; from a source's buffer when none of its rows is that old), and every channel's position moves there. So everything above the newest post read is read, as in a chat, and at the newest post of a live timeline with nothing waiting the whole feed is read, hidden posts after it included.
- `ReadMarker` sends the positions after 300 ms, and when the timeline closes, through `markViewed` (TDLib's `viewMessages` with `force_read`, which moves the position to the newest id it names): the newest post passed per channel, and with it the posts on the screen between the position Telegram has and that post. Every other post on the screen counts a view without moving the position, through `countViews` (`viewMessages` without `force_read`): a post read long ago that was scrolled back to, and a post on the screen that is not yet read. Each post is reported once per visit of the screen; TDLib answers with the fresh view counters, which reach the rows as edits.
- "Mark all read" (`MarkRead`, `feeds/mark_read.dart`) moves the position of every channel of a feed, a folder or one channel to its newest post with `markViewed`. It is in the feed's row menu, the long-press menus of the folder tabs and of "All channels", and a channel row's menu.
- Unread count of a feed (`FeedsController`), counted as Telegram counts: every post after the read position, each part of an album one post. With the "Count unread posts" switch on (`badge.countPosts`, synced, default on) the badge shows the posts; off, the number of channels with any.
  - A feed that shows everything counts Telegram's own `unread_count` of each channel, from `myChannels` and then `readUpdates`; nothing is read from the history.
  - A feed that hides some posts counts, per channel with an unread count, the posts after the read position that its filter lets through: a single post when it passes, an album with the parts `FeedFilter.shownParts` gives it. Minimized posts are not counted. They are read from `history`, newest first, in pages of 100, down to the read position, at most 1 000 per channel (the badge then reads "999+"). The count is kept: a position that moves on drops the posts it passed, a new single post is added, a deleted one is removed; a new album part, or a changed filter, counts the channel again.
  - The number of channels with news comes first, so the line under the feed's name appears at once; the filter may still take a channel away when its posts are counted.
  - The count sits on the right of the feed's row, before its menu.
- While the app is away (lifecycle `hidden` or `paused`) the timeline reads nothing: `_onPositions` returns at once. The first post that arrives then takes the "Unread posts" divider (`_dividerWhileAway`), as the official app drops its divider and inserts one above the first message that comes in while it is paused. Back in the foreground, a reader who stood at the newest post gets the list jumped to that divider like an opening at unread posts (row above the divider at 0.92, then `_settleAtNewest`), behind `_repositioning` so that the frame before the jump reads nothing; a reader further up is left alone, the posts wait as ever, and the corner button lets them in and scrolls to the divider (`_scrollToDivider`).
- The button to the newest posts carries the unread posts of the timeline (`FeedTimeline.unreadPosts`, every part of an album one) plus the posts that arrived while reading. A tap, as `onPageDownClicked` of the official app: to the "Unread posts" divider while it has not been on the screen in this visit (rebuilding the live timeline at the first unread post when a jump left the divider behind); else back to the post whose reply quote the reader tapped; else to the very end, releasing the posts that waited. Reaching the newest post forgets the reply's place, as the official app does. The button is shown while the reader is away from the newest post and something calls for it (unread or waiting posts, a jumped timeline, a reply's place to return to), or the reader's own scroll has brought it: `_followScrollForCorner` adds up the drag and fling one way, 100 px towards the newest posts show it and 100 px towards older ones hide it, as `pagedownButtonShowedByScroll` of the official app. A timeline that opens away from its newest post starts with it shown. It comes and goes through an `AnimatedSwitcher` (scale and fade, 200 ms).
- Posts carry no read mark of their own, as in the official app: the divider and the counters say what is new.

### 5.5 Sync through Google Drive

Feeds with their sources, rules and a whitelist of settings (`isSyncedSetting`: theme, post text size, "Count unread posts", `tts.*`, `media.*`, AI endpoint and model) are kept equal on all of a user's devices through one JSON file in the hidden app-data folder of the user's own Google Drive. Read state is Telegram's and reaches the other devices through Telegram. The kept timeline positions, the AI API key, the Telegram session and every other setting (background watching, rule sounds, app lock, recent searches, quick reaction) stay on the device.

- **Identity.** Feeds and rules carry a random `sync_id` (local row ids differ per device) and an `updated_at` stamp; settings carry `updated_at`. A feed's sources are part of the feed: adding, removing or reordering sources stamps the feed. A rule names its feed by the feed's `sync_id` (`feed`), and a device applies it to its own row of that feed; a rule whose feed it does not have stays out. Deleting a feed or a rule leaves a row in `sync_tombstones`, and so does every rule a deleted feed or a removed channel takes along. Logout turns sync off before wiping the database and leaves no tombstones, so an emptied database is never merged into the file.
- **Merge** (`SyncSnapshot.merge`, package `core`): item by item, the newer edit wins; a deletion beats edits made before it, and an edit made after the deletion restores the item. Tombstones expire after 180 days. The file is canonical JSON with format version 2, in which every rule belongs to a feed. A file of version 1 is read without its rules, which belonged to no feed, and is written back as version 2; a file with a newer version is refused.
- **Run** (`SyncEngine`): export the database, read the file, merge, apply the changes locally (`applySynced*` in `app_db`), write the file only if it differs from what is stored. Two devices writing at once can hide each other's edits in the file but never lose them: every run merges the device's whole local state back in, so the next run repairs the file.
- **Schedule** (`SyncController`, UI isolate): at start, 15 seconds after a local edit, every 15 minutes while the app is open, and on demand from Settings. A change notification leads to a Drive request only when the synced data differs from what the device held after its last run. Pulled rule changes reach the core through the database watchers, like local edits.
- **Drive access** (`DriveSyncStore`, `GoogleDriveAuth`): `google_sign_in` for the account and an access token with the single scope `drive.appdata`, then REST calls (`files.list` in `appDataFolder`, media download, multipart create, media update). A 401 gets one retry with a fresh token. At start the device asks only for the Drive token of the account it signed in with (`sync.account`, device-local), which needs no UI; Google's account sign-in, which shows a "Signing you in" sheet, runs only when that email is unknown. A build needs an Android OAuth client (package name and signing SHA-1) in a Google Cloud project and that project's web client id: `--dart-define=GOOGLE_SERVER_CLIENT_ID=...`. Without it the Sync screen says the build cannot sync.

### 5.6 Video playback

- **Playing while downloading.** A video starts as soon as its first bytes are there. `MediaServer` (UI isolate) is an HTTP server on the loopback interface; the player (`video_player`, ExoPlayer) opens `http://127.0.0.1:<port>/<secret>/<fileId>` and asks for byte ranges. Bytes TDLib already has are read from its partial file, where they sit at their final offsets; for a range that is not there yet the download is aimed at it (`downloadFile` with `offset`) and the response waits. Seeking, and MP4 files with the index at the end, are the same case. The newest request decides where TDLib downloads. Response headers are written at once through a detached socket, because `dart:io` holds them back until the first body byte and the player's read timeout would run out meanwhile. The path contains a random token, since other apps can reach the port; the port closes when nothing plays. A finished file plays from disk without the server; a file without a known size is downloaded whole first.
- **Sessions.** `VideoSessions` keeps one `VideoSession` (player plus state) per file id outside the widget tree, so the timeline row and the viewer show the same player. Only one session has sound at a time, and a track that starts in `AudioSessions` takes the sound from it (`AudioSessions.beforeSound`, which `VideoSessions.quietAll` answers: an autoplaying session is muted, any other paused). Timeline rows are keyed by post, so a new post at the top cannot shift player state under another post.
- **Viewer controls** (`MediaViewerScreen`, `VideoStage`, `ZoomablePhoto`; paging in section 5.13): a tap on a video in the timeline opens it in the viewer and plays it there; the timeline has no player controls. Only the page in front has a session: its neighbours are posters, and turning the page hands the session back exactly as leaving does. The viewer hides the status bar and keeps the navigation bar (`SystemUiMode.manual` with the bottom overlay), as the official viewer does, because with the navigation bar hidden Android gives the first swipe from a side edge to the app and goes back only on the second; pages turn with swipes that start inside the screen. The viewer follows the device's orientation. Controls: back arrow; a tap shows or hides them; a scrubber with the buffered range; speed; mute; rotate, on a video wider than tall; play again from the start at the end. While the scrubber is dragged the player is sent to the place under the finger every 150 ms at most (`_showFrameAt`), but only when the file is on the phone or the place lies in a buffered range: a place still to be downloaded waits for the finger to lift, so the download is not aimed from place to place. Rotate asks Android for landscape, or for portrait when the screen is in landscape (`SystemChrome.setPreferredOrientations`), and the stage hands the choice back to the device when it goes. A double tap on the left or right third seeks 10 s, and while that seek lasts (700 ms after its last tap) every further tap on the same side goes 10 s more at once: a layer over the gesture layer takes those taps, since under the double-tap detector a third tap would wait for a fourth. The steps count from where the seek began, not from the player's lagging position. On the other side a tap starts a count of its own, which seeks from its second tap; in the middle it ends the seek. The hint at the side shows the seconds so far. In the middle a double tap zooms to 2.5× around the tapped point and back. A pinch zooms up to 6× and a drag moves the zoomed picture (`InteractiveViewer` around the player's texture; zoom helpers in `media/zoom.dart`, shared with photos). A finger held down seeks until it lifts (`HoldSeek`, after the official app's `VideoPlayerRewinder` and `OldVideoPlayerRewinder`): on a video of eight seconds to three minutes it starts at 2×, or at 2× backwards on the left third, and a slide changes the speed by one for every 40 px, between 6× backwards and 10× forwards, turning round under 0.4×; on a longer video the right third runs at 4×, 7× and 13× and the left third rewinds at 3×, 6× and 12×, a step every two seconds. Forwards is the player's playback speed. Backwards the player is paused and `VideoStage` walks a position back on a 100 ms timer and seeks the player to it every 200 ms (400 ms on a long video); lifting the finger seeks to that position and gives back the speed and whether the video played. A zoomed picture is not sought by holding. The speed menu's first line is `SpeedSlider`, 0.2× to 2.5× in tenths, which the player follows while it is dragged. The gesture layer lies behind the buttons, so button taps do not wait out the double-tap window. A vertical drag with one finger carries the picture away while the black behind it fades, and closes the viewer past 120 px or with a flick (`SwipeToClose`); it is off while the picture is zoomed, and a second finger leaves the drag to the pinch. The viewer's route is not opaque, so timeline rows under it stay visible to the visibility detector; autoplay rests while the row's route is not the current one. Leaving the viewer pauses the video, disposes the player and cancels an unfinished streaming download at once (`releaseFromViewer`). A video opens in the viewer at the place it was left there (`VideoPositions`, `media/video_positions.dart`): the share of the video that was watched, by the file's remote id, kept in memory for a video of ten seconds or more and in the account's `video-positions.json` (`AccountStore.videoPositionsOf`, at most a hundred places) for one of five minutes or more. The session writes the place when the viewer lets go of it and every five seconds while the viewer plays it, but not between the moment the viewer takes the session and the moment it has put the video where it starts (`_entering`), so the place a row happened to be at is never taken for one the viewer left; a place at the start or past 99.9 % is none. A video the timeline was autoplaying, which has no place of its own, starts from the beginning in the viewer; one taken over from the mini player or the system window keeps its position. The viewer says whether the video loops (`retainForViewer(loop:)`): a GIF and a video of up to thirty seconds do, and a session shared with an autoplaying row, which loops there, takes the viewer's choice while the viewer holds it and the row's again afterwards. A video that does not loop is brought back to its start by `VideoStage` once the player stands paused on its last frame, with the controls shown. A logout deletes the places, and removing an account deletes its file.
- **Download button** (`VideoDownloads`, `VideoDownloadButton`): a pill in the top left corner of a video in the timeline: arrow and size, then a progress ring with the bytes that cancels on tap, nothing once the file is complete. In the viewer's top bar the same button is `compact`: the ring alone while the file downloads, and nothing otherwise, because the viewer's menu is where a download is asked for. It downloads the whole file into TDLib's cache (priority 16, below a playing video's 32). A download the user asked for is not cancelled when its player closes, and cancelling it leaves a playing video its stream. Posts carry the `FileRef` of the time they were loaded, so the button asks TDLib (`getFileDownloadedPrefixSize`) whether the file is complete by now, and follows the file's progress while it is shown.
- **Picture-in-picture** has two parts. *Mini player* (`MiniPlayer`): the viewer's PiP button moves the session into a small window in the root navigator's overlay that floats over every screen; one scale recognizer moves it with one finger (it rests at the nearer side) and resizes it with two, between 120 px and the width of the screen, keeping the video's shape. While a finger moves it the window may leave the screen sideways: let go over an edge while still moving out at 700 px/s or more, or more than half its width out, it closes; otherwise it comes back to the side. A tap shows the buttons (play or pause, back to the viewer, close) for three seconds while the video plays, a double tap seeks ten seconds by the half it was on. `MiniPlayer` keeps the place and the width of the last window in memory, and the next one opens with them. A session counts its sound-watching holders (`retainForViewer` / `releaseFromViewer`), so the viewer and the mini player hand a video to each other without stopping it, and it ends when the last one lets go. Opening the viewer ends a mini player that shows another video. *System window* (`SystemPip`, `PipHost`, `MainActivity`): Android's picture-in-picture shrinks the whole activity, so it takes over only when the app is left. While a video plays in the viewer or the mini player (`VideoSessions.foreground`, counted once the player is initialized, because the window needs the picture's size) the activity is armed over the channel `tf/pip` with the video's aspect ratio, clamped to 1:2.39 to 2.39:1: auto-enter from Android 12, `onUserLeaveHint` on 8 to 11. The parameters carry one `RemoteAction`, pause while the video plays and play otherwise, with the label in the app's language (`arm` hands over `playing`, `playLabel` and `pauseLabel`). Its tap is a broadcast to a receiver the activity registers unexported, which calls `pipAction` on the channel; `SystemPip` toggles the foreground video, or the one that was in front last, since a paused video is not in `VideoSessions.foreground`. For the same time the window keeps the screen on (`tf/app.keepScreenOn`, `FLAG_KEEP_SCREEN_ON`). In the window, `PipHost` (above the navigator) shows only the video and keeps the screens alive offstage. When the activity is stopped the foreground video pauses; nothing plays from the background.
- **Round video messages** play in their row (`VideoView._playInCircle`): a tap starts the message from its beginning with its sound and without looping, and pauses what plays as sound (`pauseForVideo`); when it has played to its end the row puts it back to a silent loop and the sound plays on. `RoundFloat` (`media/mini_player.dart`) is the round window in the root overlay that takes such a message over while it plays with sound and its row is out of sight: the row asks for it when less than a fifth of it is visible, and from its `dispose` when it is let go in one move (the window then appears with the next frame). The window holds the session with a plain `retain`, so the message plays on without its row and nothing starts over; it lets go when the row is three fifths visible again, on its cross, and when the message has played to its end. It stands under the header, the home screen's row of tabs and the banner there: `StatusBannerHost.heightUnderHeader` says roughly how much room the banner takes.
- **Autoplay** (section 5.14 decides which videos): a video that loads by itself starts muted and looping in its row (`InlineVideo`) once 60 % of it is visible, and pauses below 20 %; it streams through the loopback server while its automatic download goes on. A tap opens the viewer on the same player with sound; leaving the viewer mutes it again and it keeps autoplaying. A row the list rebuilds picks its autoplay session up again within 0.8 s; after that the player is disposed, and the download continues only if the automatic download wants the file.

### 5.7 Main screen

`HomeScreen` is a tab bar of "Feeds", the Telegram chat folders and "All channels". The app bar holds the search over all channels, the pause (`PauseButton`, section 6.2), Rules and Settings. A floating button on the Feeds tab creates a feed and opens its channel editor; it shows only while the Feeds tab is up.

- `ConnectionTitle` sits in the app bar of the home screen and of every timeline. It follows the gateway's `connection` stream (TDLib's `updateConnectionState`, carried over the core port as `CoreStream.connection`) and puts "Connecting…", "Waiting for network…", "Connecting to proxy…" or "Updating…" under the title until TDLib is ready.
- The Feeds tab lists the feeds, each with its count (section 5.4) and a line naming the channels with new posts (`FeedsController`). The tab label carries the feeds' posts together, or the number of feeds with any. A tap opens the feed as `TimelineScreen(feed:)`; dragging reorders; the row's menu leads to its channels, its rules, rename, mark all read and delete.
- Folder tabs come from `chatFolders()`: TDLib announces the folders in `updateChatFolders`; the chats of each are read with `getChats(chatListFolder)`, which applies the folder's include and exclude rules and Telegram's order, and only channels are kept. A folder without channels gets no tab. The app never edits folders. The `TabController` is replaced only when the set of folders changes, and the selected tab stays selected.
- `Channel.lastMessageAlbum` is everything the newest post carries, oldest part first. TDLib's chat carries one message, so when that message has a `media_album_id` `TdlibGateway._albumOf` reads the ten messages before it (`getChatHistory`, once per newest message) and keeps those of the same album; the album's words are taken from whichever part has them. `ChannelTile` draws the photos and videos among them as `RowThumbnail`s, three at most, from Telegram's inline minithumbnail where there is one, so the list downloads nothing for them; `albumLabel` names an album without words. `Channel.isMuted` is the chat's `mute_for`, or with `use_default_mute_for` the `mute_for` of `notificationSettingsScopeChannelChats`, asked once.
- "Mark as unread" in a channel row's menu is Telegram's own flag (`markChannelUnread`, TDLib's `toggleChatIsMarkedAsUnread`; `Channel.isMarkedUnread` is the chat's `is_marked_as_unread`): no post becomes unread. The row draws an empty `UnreadBadge`, the tabs count the channel, and opening the channel or marking it read takes the flag off (`HomeScreen._markUnread`).
- A tab's badge counts channels with unread posts, never posts, as the official app's tabs count chats: a folder tab and "All channels" by Telegram's own `unreadCount` per channel (`_unreadChannels`), the Feeds tab by `FeedsController.unreadOnTab`. The "Count unread posts" switch changes the counters of the feeds only.
- Every tab's list scrolls with a controller of its own (`_tabList` wraps it in a `PrimaryScrollController`), so a tap on the tab that is already open (`_onTabTap`: the tab bar's controller is not changing) animates that list to its top.
- `myChannels()` walks the main chat list and every folder list, each channel once, because a channel joined through a folder invite link is in its folder's list and in no other. The home screen asks for the folders first so the gateway knows which lists to walk. The archive is not walked, so an archived channel appears in these lists only when a folder holds it.
- The archive has a row of its own at the top of All channels: `archivedChannels()` walks `ChatListArchive` when that row is tapped and shows the result as an ordinary channel list.
- A long press on "All channels" offers "Mark all read" for every channel of the main list. A long press on a folder tab offers "Create feed from folder" (a feed with the folder's name and its current channels in the folder's order; the feed does not follow the folder afterwards) and "Mark all read".
- Every tab carries its own padding (the bar's `labelPadding` is zero) and is at least 72 px wide, so the long press covers the whole tab, including a folder named with a single emoji.
- A long press on a channel row opens its menu (mark as read, channel info, add to a feed) under the finger: the row is wrapped in a `GestureDetector`, since a `ListTile`'s own long press reports no position.
- Channel lists (`ChannelList`) show photo, newest post, its date (`formatListDate`, the official `stringForMessageListDate`: the time today and for last night within eight hours, the weekday within a week, `listDatePattern` within a year, `dd.MM.yy` before that; the search's result rows use it too) and Telegram's unread count from `Channel` (`UnreadBadge`: the whole number, grey for `Channel.isMuted`), with the tags of the feeds the channel is in at the end of the preview line (`AppDatabase.feedNamesByChat`, live through `watchFeeds` and `watchSourceChanges`). A row (`ChannelTile`) is the official app's: 70 high (`ChannelTile.height`) with a photo of 52, the name with the verified mark (`Channel.isVerified`, the supergroup's `verification_status`) and the date on the first line, the preview, the feed tags and the counter on the second, and a hairline under the words. Every row has both lines, whatever a channel has, and the initials of a channel without a photo take its own colour (`peerColor`). The feed editor's channel picker carries the same tags. A new post moves its channel at once (`HomeScreen._bump`): the row takes the post as its preview (`Channel.withNewestPost`) and goes to the top of the main list and of each folder that holds it, under the channels pinned there (`Channel.pinnedLists`, from the chat's `positions`: 0 for the main list, a folder's id for that folder). `ChannelList` slides the rows that changed place from where they were (one `AnimationController` for the list, since a sliver builds its rows by place and a row's own state would not survive the move). Lists reload when the app resumes, three seconds after a new post, and on pull to refresh; between reloads the rows' counters and the folder tabs' badges follow `readUpdates` (`Channel.withRead`), in the Archive too.
- A channel opens as `TimelineScreen(channel:)`: the same timeline with one source. It reads and moves Telegram's read position like a feed does (section 5.4).
- Saved Messages is the chat with oneself, handed over by `savedMessages()` as a `Channel` titled "Saved Messages" and opened from Settings as an ordinary timeline (`TimelineScreen.savedMessages`). It belongs to no feed. Its posts offer no Share, Copy link or Save to Saved Messages, in the menu, the selection bar and the viewer: a post there has no link of its own and is saved already. `TdlibGateway` sends a `PostAdded` for a new message of that chat once Telegram has it (`updateNewMessage` without a sending state, or `updateMessageSendSucceeded`), so a post saved elsewhere appears in the open screen. Its posts can be deleted, from the post menu or the selection bar, after a dialog worded as the official app's: `deleteFromSavedMessages` calls `deleteMessages` in the chat with oneself without `revoke`, and the post leaves the timeline when TDLib's `updateDeleteMessages` for that chat arrives as `PostsDeleted`, which the gateway passes on for channels and for Saved Messages only. It is the only deletion the app makes.

### 5.8 Feed filters

`feeds.filter_json` holds a `FeedFilter` (package `core`): media presence (any, with media, text only), a set of media kinds (photo, video, gif, audio, voice, document, other; empty means all), a minimum video length, a minimum length for posts without media, a condition on the words (`text`, the `Expr` of the rules, section 6.1), `wholePost` (true unless the JSON says otherwise) and `minimize`. Null means everything. Unknown values are ignored; broken JSON shows everything; a condition that cannot be read, or `And([])`, is no condition.

- **Deciding a post.** `FeedFilter.shownParts` takes a single message or the parts of an album and gives the parts the feed shows, or none. The words are matched as a rule matches them (`RuleEvaluator`), over all captions of the post together, joined by line breaks, so an album goes by its caption whichever part carries it. A post without words is an empty text: a "must not contain" term lets it through, a word it should have does not. The four content settings judge the parts one by one; with `wholePost` one part that passes carries the others, without it only the passing parts show. An album whose parts all fail stays out.
- **One message alone.** `allows` (the shared media tabs, which list single items by kind) and `mayShow` (a message that may ride along in its album: rules, search, the dry run) cannot see an album's siblings. An album part without a caption passes their word check, and `mayShow` checks only the media presence for a part that `wholePost` carries.
- **Timeline.** `FeedTimeline` keeps every part of every album it has taken, shown or not (`_albums`), and decides the row again with `shownParts` whenever a part arrives, is edited or is deleted, so a caption that comes last can take an album away or bring it. While paging back, a page ends only after the rest of the album at its end has come in, from the source's buffer or its next page. An edit decides a post again, so words edited into or out of a match move it in or out of the feed. Posts no row shows are remembered with their dates for the read state.
- **Minimized.** With `minimize`, a post the filter leaves out is a row of its own with all of its parts and `TimelineItem.minimized` set. `MinimizedPost` (`feeds/post_card.dart`) draws it as a bubble of one line: the channel's name in its colour, the beginning of the words (`postLabel`) and the time. A tap opens it for the visit (`TimelineScreen._opened`), the menu's Minimize folds it again, and a post the timeline opens at (a notification, a reply quote, a link) is opened. A minimized row counts as hidden: `isUnread` is false for it, so it carries no divider and adds nothing to the button or the badge; it is read as a row with the posts around it, sends no view while folded, and its pictures join the viewer only once it is open.
- **Waiting posts.** A post that arrives while the reader is further up waits in `_pending`, except a single post the feed does not list at all, which is hidden at once. `pendingNew` counts what the button shows (every part of a shown post), `hasPending` whether anything waits, minimized posts and album parts included; reaching the newest post releases them all.
- **Read state.** Hidden posts must not stay unread, or a channel that only posts hidden things would keep its feed marked as new. `passedAt` counts the hidden posts with the rows around them: a hidden post older than the newest row read is read, and at the newest post of a live timeline all of them are.
- **Rules.** A rule sees the posts of its own feed as that feed shows them: the engine gets every feed with its channels and filter (`feedsForRules`), and a rule is only evaluated for a post its feed's filter lets through (`mayShow`); a minimized post is not let through. The caption of an album notifies when the feed shows whole posts, so a rule can notify about an album the timeline hides; the error is on the side of notifying.
- **Search.** `FeedSearch` asks `mayShow` for a search by words and `allows` for the shared media tabs.
- **Editing.** The feed editor's "Show" row opens a sheet with the four content controls, the words ("Text content": the rule editor's `ConditionEditor`, builder and text form), the "Show the whole post" checkbox (enabled only for a feed with media) and "Show minimized"; the row's subtitle is the filter in words, the condition in its text form. A condition that cannot be read keeps the sheet open with the error under the field.
- **Sync.** The filter travels with the feed as the optional `filter` key of the sync snapshot.

### 5.9 Posts and comments

Screens use `SwipeBackTransitionsBuilder` (`widgets/swipe_back.dart`) on every platform (`appPageTransitions` in `main.dart`): they slide in with Flutter's Cupertino transition and go back with a swipe to the right that may start anywhere on the screen, as in the official app. The gesture is a horizontal drag recognizer over the whole route that counts once the finger has gone 25 px (0.4 cm) to the right and then drives the route's own animation; let go past a third of the width, or flung, the screen pops. A sideways scroller inside the screen takes its drags first, a vertical scroll claims the gesture before 25 px of sideways movement, and a route that may not be popped (`popGestureEnabled`: an open selection or search) does not move. The media viewer keeps its own see-through route and its swipe down.

A timeline row (`PostCard`, `feeds/post_card.dart`) is drawn like a post in the official Android app, except that nothing stands beside the bubble, so text and pictures get the whole width. A bubble on a tinted backdrop (`ChatColors`) starts with its title line (`BubbleTitle`): the channel's name in one of Telegram's seven peer colours (`peerColor`, by id) and the channel's photo, small, at the right end of that line. Then media edge to edge, the text, reaction pills and a comments bar. Day pills stand between days.

- Service messages: `mapping.content` turns the kinds a channel has (`messagePinMessage`, `messageChatChangeTitle`, `messageChatChangePhoto`, `messageChatDeletePhoto`, `messageSupergroupChatCreate`, `messageVideoChatStarted`, `messageVideoChatEnded`, `messageVideoChatScheduled`) into a `ServiceNote` media with a `ServiceKind`, and every other message content that is not a post (`_isContent`) into `ServiceKind.other`. The timeline draws a `ServiceNote` as a `ChatPill` with `AppLocalizations.serviceLabel`, naming the channel in a feed; the pill of a pin jumps to the pinned post. `RuleEngine.evaluate` skips them, `FeedFilter` shows them only when it filters nothing, and they are never minimized rows. `messageAnimatedEmoji` maps to a text post with the emoji. Content the app does not draw is an `UnsupportedMedia` chip named by `unsupportedLabel`, which falls back to "Unsupported post".
- The pin of a pinned post (`Post.isPinned`, kept current by `updateMessageIsPinned`), views, the author's signature (`Post.signature`, TDLib's `author_signature`, which gives way when it is long), "edited" and the time sit in the bottom right corner (`PostFooter`). A text of nothing but emoji (`emojiOnlyCount`, by grapheme, and no formatting but custom emoji) is drawn at the official app's sizes for it (`emojiOnlySize`: 40.8 px for one or two, then 33.6, 26.4 and 22.8; custom emoji alone a step or two larger). `BubbleText` is a render object that puts this footer on the last line of the text when there is room and on a line of its own otherwise. With reactions, the pills use the full width and the footer takes the free end of the last row. With nothing under the pictures it lies on top of them.
- A double tap sends the quick reaction (`reactions.quick`, a thumbs up until the reader picks another in Chat settings from `standardReactions`, Telegram's own list; the timeline watches the setting). Before it sends, `_quickReact` asks what the channel allows (`availableReactions`, once per channel and visit) and does nothing when the emoji is not among it. A second double tap takes it back. A reaction that was just set makes its pill swell and settle (`ReactionPop`, for 600 ms through `_justReacted`). The menu's strip (`ReactionStrip`) shows five reactions and an arrow that turns the strip into a panel of all of them. The bubble counts its taps itself (`BubbleTaps`, an `InkWell`): two within 300 ms and 48 px send the quick reaction, one opens the menu once those 300 ms have passed, as the official app waits when a quick reaction is set. Links, pictures, pills and the comments bar answer their own taps at once. The pictures of a post without words carry a double-tap recognizer of their own, because a picture's tap would open the viewer before a second tap could arrive.
- A tap on the bubble opens the menu as a popup at the point that was touched, over a dimmed screen (`showPostMenu`, `feeds/post_menu.dart`): the reactions the channel allows in a strip of their own above the lines, then Comments, Copy text, Copy link, Share, Save to Saved Messages, "Save to gallery", "Save to downloads" or "Save to music" where the post has pictures or videos, documents, or music (`_saveToDevice`), Report (`_report`: `gateway.report` is TDLib's `reportChat`, called again with each answer until it says `ReportDone`; a `ReportChoice` is a sheet of reasons, a `ReportText` a dialog for words; Saved Messages has no Report), Minimize (on an opened minimized post), on posts with a video "Autoplay and download settings", which opens Data and storage, Delete (in Saved Messages, in the error colour), and behind a line Open in Telegram. The popup is moved up and sideways as far as it takes to stay on the screen, and its lines scroll when they do not all fit. `saveToSavedMessages` forwards the whole album into the chat with oneself, keeping the channel as the source.
- Every bubble takes the whole row, whatever it holds, so the posts of a timeline line up.
- "Copy text" copies the row's words. Every `TextEntityKind.pre` block ends with a copy button of its own (a `WidgetSpan` inside the text, so it sits where the block ends).
- A long press starts a selection, as in the official app, and the finger that made it picks every row it is dragged over (`startSelection`, `dragSelection`: the rows between the one the press began on and the one under the finger, found through the list's item positions; going back lets them go). One `GestureDetector` wraps the row in both of its states, so the long press that began on a plain row is still followed once the row is a selectable one. A selection holds up to 100 posts (`maxSelected`); a further one is refused with a vibration. `Haptics` (`host/haptics.dart`) gives each touch the feedback the official app gives it: `longPress` is Android's `LONG_PRESS` (`HapticFeedback.vibrate`), `reaction` its `KEYBOARD_TAP` (`mediumImpact`), and `refused` a vibration of 200 ms, which no feedback constant gives, so the activity vibrates itself (`tf/app` method `buzz`). `TimelineViewState` keeps the picked rows by `(chat id, row id)`, each card gets a tick and a layer that swallows every other tap, and `TimelineScreen` replaces its app bar with "N selected" plus Copy text, Share and Save to Saved Messages (and Delete in Saved Messages), which run over the picked rows oldest first (saving groups them per channel, so an album goes in one call).
- The post text size (`appearance.postTextScale`, a factor of the standard size 16: 0.75 to 1.875 for the sizes 12 to 30 the slider offers, synced) comes from `PostTextScale`, an inherited value above the navigator. `PostCard` and the comments wrap themselves in a `MediaQuery` whose `textScaler` is clamped to that factor, so posts follow the setting and the rest of the app follows the system.
- The list keeps 8 px plus the system inset under the newest post, which in the reversed list is the bottom edge of the screen.
- A forwarded post carries `Post.forwardedFrom` (`ForwardOrigin`: the name, the origin chat and post, the origin user, the author signature, and whether the sender hides itself). TDLib gives ids, not names, so `TdlibGateway._post` resolves them through the sender cache the comments use: one `getChat` or `getUser` per origin and session. `ForwardedFrom` draws "Forwarded from <name> (signature)" under the title line; a tap opens the original post when the account follows that channel, and says so otherwise.
- A post that answers another carries `Post.replyTo` (`ReplyTarget`: the answered post's chat and id, the quote with `manualQuote` when the author picked one, the words otherwise, a thumbnail, and the name for a reply across chats). TDLib sends the origin and content only when the answered post is in another chat; inside the channel `TdlibGateway._reply` fetches that post once and keeps its words and thumbnail in a map cleared past 500 entries. `RepliedPost` draws the block above the text; a tap jumps to the post when it belongs to the timeline's channels, else opens that channel.
- `LinkPreviewCard` draws the author in the title's place when the preview has no title, the description in up to six lines, and for every kind but `web` a last line that names what the link opens; the whole card stays one tap target. `Post.captionAbove` (`show_caption_above_media` of a photo, video or animation) moves the words over the pictures; the pictures then end the bubble and carry the footer when no reactions follow.
- `formatCount` shortens views, reactions and subscribers like the official `formatShortNumber`: K and M with one decimal that is cut off and left out when zero. A file row (`DocumentView`, and `FileRow` of the shared media) starts with `FileThumbnail`, the document's thumbnail when TDLib has one, and a tap on a downloaded file calls `openDownloadedFile`: the `tf/app` method `openFile` hands the path to Android with `ACTION_VIEW` through the app's `FileProvider` (authority `<package>.files`, `res/xml/file_paths.xml`), answering false when no app takes the type. `ThreadScreen` gets the timeline's `_openTelegramLink` as `onOpenTelegramLink`, so links from comments open followed channels in a screen of their own.
- More kinds of content have media of their own (`feeds/extra_media.dart`): `LocationMedia` for `messageLocation` and `messageVenue` (`LocationView`: the picture of the map from `mapThumbnail`, TDLib's `getMapThumbnailFile` at zoom 15 in the width of the bubble, a pin over it, the venue's name and address under it; a tap launches `geo:` and falls back to a maps link), `ContactMedia` (`ContactView`, which dials), `GameMedia` (`GameView`: title, description, photo; the game's own words are the post's text) and `ChecklistMedia` (`ChecklistView`: tasks with `completion_date` set are ticked). A `messageDice` becomes the `StickerMedia` of its final state, or its emoji as the post's text when TDLib has no single sticker for it. In lists and notifications such posts are named by their title or their kind (`mediaLabel`); a feed's media filter counts them as `other`.
- A post's inline keyboard (`reply_markup` of kind `replyMarkupInlineKeyboard`) becomes `Post.buttons`: the buttons of type `inlineKeyboardButtonTypeUrl` as `UrlButton`s in their rows (`mapping.urlButtons`), every other kind left out and a row without a link button dropped. `PostButtons` draws them under the bubble in the colours of the date pill, the arrow of a link in each corner; an album shows the buttons of whichever part has them. A tap goes through `confirmOpenLink` unless `hidesTarget` says the link leads into Telegram, and then to the timeline's `_openLink`.
- `PhotoMedia.miniature` and `VideoMedia.miniature` hold TDLib's `minithumbnail` (a JPEG of some forty pixels, base64, part of the message itself). `MediaMiniature` decodes it once and draws it blurred to fill the picture's place. `Downloaded` hands a stand-in everything about the wait (`DownloadWaiting`: bytes that came, the total, `start`, `cancel`); `PhotoView` draws the miniature under a ring with a cross (`cancel` calls `cancelDownload` and keeps the download from starting again by itself) and the loaded size in the top left corner, or the download badge with the file's size when the download waits for a tap. `VideoView`'s poster uses the miniature until the thumbnail is there.
- `PhotoMedia` and `VideoMedia` carry a `MediaCover`: `spoiler` from `has_spoiler` of the message content, `sensitive` when the message's `restriction_info` says `has_sensitive_content` (it wins over a spoiler). `MediaView` wraps such media in `CoveredMedia` (`feeds/media_cover.dart`): the real picture or player is built underneath, out of reach of touches and of screen readers, and a `BackdropFilter` blurs it where it stands, so uncovering moves nothing. A tap uncovers a spoiler; content for adults asks first. The uncovered file ids are kept in memory for the life of the process. A round video message is not covered.
- A post with a link carries TDLib's `linkPreview` as `Post.linkPreview` (`LinkPreview`: url, display url, `LinkKind` (what a link into Telegram leads to, from the preview's type: a channel, a group, a message, a user, a bot, a wallpaper, a theme, a sticker set, a video chat, a story, a boost, a chat folder or a web app; `web` for everything else), site, title, author, description as plain text, a `PhotoMedia` for the picture, the video flag with its length, and TDLib's `show_large_media`, `show_media_above_description` and `show_above_text`). `_previewPicture` reads the picture out of each kind of link (photo, article, app, video with its cover, embedded player thumbnail, animation, document, audio cover); kinds without one (chat, sticker set, invoice, unknown kinds) give a card of words alone. `LinkPreviewCard` (`feeds/link_preview.dart`) draws an accent bar and a tint in the channel's peer colour, the site in that colour, the title, a description of at most three lines, and the picture either the width of the card or as a 56 px square beside the words, with a play badge and the length on a video link. A tap opens the link through `onOpenLink`, like a link in the text. A preview is not `Post.media`: a feed that shows text posts only still shows a post with a link.
- A channel's timeline carries `PinnedBar` (`feeds/pinned_posts.dart`) at the top when `pinnedPosts(chatId)` finds any (TDLib's `searchChatMessages` with `searchMessagesFilterPinned`, paged, newest first). The bar shows one of them, as the official app's does: the newest one that is not newer than the newest post on the screen (`_showPinAt`, the official `findClosest` over the highest visible id), or the oldest when the reader is above them all. The line at its left has a piece per pinned post, three at most, with the piece of the post on show lit. A tap jumps to that post and forces the bar on to the next older one, from the oldest back to the newest (`_pinForced`, the official `forceNextPinnedMessageId`); the reader's own scroll lets go of it, at once towards newer posts or after the wrap, and towards older posts once the list is past that pin. With several pinned posts the button at the right opens `PinnedPostsScreen`, which draws them as cards that take no touches of their own: a tap anywhere on one pops the screen with that post and the timeline jumps to it, and "Hide pinned posts" pops it with `true`. With one pinned post the button is a cross. Hiding writes the id of the newest pinned post to the setting `pins.hidden.chat.<id>` (the official `pin_<dialog>` preference): the bar is shown while that id is not the newest pinned post's, so a newer pin brings it back. The floating day pill stands below the bar. A feed mixes channels and has no bar.
- The day of the topmost row floats over the list (`FloatingDay`, the same pill as between days). It fades in when the reader starts a scroll (`UserScrollNotification` with a direction, so opening a feed, a date jump or a new post brings nothing out), follows the top of the screen from `itemPositions`, and fades out 900 ms after the list comes to rest, leaving the tree. A tap goes to the first post of that day (`jumpToDayStart`: an animated scroll when that post and a row older than it are loaded, `jumpToDate` otherwise). Both the pill between days and the floating one word the day with `formatChatDay`, the official `formatDateChat`: day and month, and the year from 365 days away. A scroll notification can arrive from inside the list's layout, where a rebuild must not be scheduled, so the pill's state lives in two `ValueNotifier`s written after the frame.
- Pictures in the list decode at the size they are drawn (`fileImageFor` in `feeds/media_view.dart`, a `ResizeImage` over the file): a photo cell, a video's cover, a custom emoji and a channel photo take the pixels of their box, cropped side first for a cell. A 1280 px photo decoded whole takes 6.5 MB, and the image cache of 100 MB would hold only a few screens of them. The media viewer decodes the file whole, for zooming.
- The comments bar (`CommentsBar`) draws `Post.recentCommenters` (TDLib's `recent_replier_ids`, at most three, named and pictured through the gateway's sender cache, so each person costs one lookup per session) as overlapping discs with the newest on top, the count in full, and a dot for `Post.hasUnreadComments`: the official rule, `last_read_inbox_message_id` is set and older than `last_message_id` of the reply info. Without known commenters it shows the bubbles icon.
- An album's reactions and comments are those of its first message, where Telegram keeps them and the official app reads them (`findPrimaryMessageObject`): `TimelineItem.reactionPost` and `TimelineItem.threadPost` name the part that holds them, the oldest part when none does. The pills, the menu's strip, a reaction that is sent and the comments bar go by them; the row's own identity (`rowId`, the link, the viewer's key) stays the newest part's.
- Reaction pills are painted boxes with a tap recognizer, not `Material` with an `InkWell`: a post carries up to a dozen of them. `Reaction.emoji` names the reaction: a plain emoji, `custom:<sticker id>` for a custom emoji (`customReaction`, `customReactionId`), or `paidReaction` (`mapping.reactionName`, `mapping.reactionType`). `ReactionGlyph` (`feeds/reaction_glyph.dart`) draws an emoji as text, a custom emoji as its sticker (`TelegramGateway.customEmoji`, kept by id) and the paid reaction as a star; the pills and the menu's strip use it. `availableEmoji` offers a channel's plain and custom emoji without those only Premium may send; the paid reaction is drawn with its count and is not sent.
- A sticker (`StickerMedia`) is drawn by `StickerView` at its own proportions, about 180 px on its longest side: `webp` as a picture, `tgs` through `Lottie.file` with `LottieComposition.decodeGZip`, `webm` as a silent looping video (`LoopingVideo`). A round video message is `VideoMedia.isVideoNote`, the ordinary player inside a `ClipOval` of 200 px. Neither opens the media viewer. Both carry a name for read-aloud, search and rule notifications ("A Sticker", "Video message"). A sticker counts as `other` for a feed's media filters.
- Albums of photos and videos are a mosaic: `layoutAlbum` ports Telegram Desktop's grouped layout, `Ui::LayoutMediaGroup` (fixed arrangements for two to four pictures by their proportions, row splitting towards a 3:4 block for more). The mosaic fills the bubble's width and is at most one and a half widths tall; cells crop their picture. Audio and documents of an album stay a list.
- A custom emoji is `TextEntityKind.customEmoji` with the sticker id. `FormattedText` asks the gateway for the stickers of all ids in one text at once (`customEmoji`, TDLib's `getCustomEmojiStickers`, cached in the gateway) and draws each as a `StickerView` the height of a line. Without an answer the plain emoji in the text stands.
- `Comment.media` carries what a comment holds (`mapping.content`, as for a post). `CommentBubble` draws it above the words with `MediaView`, or `StickerView` for a sticker; a photo or video opens in the viewer by itself. A bubble with media has a fixed width (280, a sticker's 180), because a picture cannot report an intrinsic width; a bubble of words is as wide as they are.
- `Post.entities` and `Comment.entities` carry TDLib's text entities (offsets in UTF-16 units). `FormattedText` cuts the text at every entity boundary, so nested and overlapping formatting works. Quotes and code are blocks: with any of them (`blocksOf`: the `quote` and `pre` entities that stand in no other block) the text becomes a column of words, `QuoteBlock`s and `CodeBlock`s, each built from the spans of its own range, and the line break between a block and its neighbours is dropped as the block's edge. A quote of TDLib's `textEntityTypeExpandableBlockQuote` (`TextEntity.expandable`) that measures more than three lines shows three until tapped, with an arrow in its corner; a `pre` entity carries the `language` of `textEntityTypePreCode`, shown in a header beside the copy button. `BubbleText` puts the footer on the last line of the words such a column ends with, and under it when it ends with a block. Links, mentions and e-mail addresses open through `launchFirst`; spoilers are covered until tapped. As in the official app: a link whose words are not its own address asks "Do you want to open …?" first (`FormattedTextState.hidesTarget`; links into Telegram and addresses that are no web pages are not asked about); a long press on a link opens a popup with Open and Copy link (`TapOrHoldRecognizer`, a tap recognizer that brings a long press along, since a span takes one recognizer and its paragraph must know it as a tap); a hashtag or cashtag (`TextEntityKind.hashtag`) opens the timeline's search with the tag in it; a phone number (`TextEntityKind.phone`, a `tel:` address) opens a popup with Call and Copy number; a tap on inline code copies it, unless the post is protected. Rules, read-aloud, sharing and notifications use the plain text.
- Avatars: the timeline takes channel photos from `myChannels()` (the database keeps titles only). Comments carry `authorId` and `authorPhoto`, resolved once per sender by the gateway. The thread view (`ThreadScreen`) shows the post as its timeline row on top and comments as bubbles with the same title line (author's name, photo at its right end); the account's own comments sit on the right without name and photo. Its list is turned over like the timeline's (`ScrollablePositionedList`, index 0 the newest comment at the bottom, the post as the last row at the top), so older pages join at the far end without moving what is on the screen; the post's row fetches the next page when it is built. `Thread.lastReadId` and `unreadCount` (TDLib's `last_read_inbox_message_id` and `unread_message_count` of the thread) decide where it opens: with unread comments the pages down to the read one are loaded (300 comments at most) and the list starts with the row above the first unread comment at 0.92, an `UnreadDivider` over that comment; otherwise at the newest comment. Comments whose lower edge has been on the screen are reported 300 ms later with `markCommentsViewed` (`viewMessages` with `messageSourceMessageThreadHistory` and `force_read`), and once more when the screen closes. The title is `postCommentCount` of Telegram's count plus what arrived since. The feed editor, channel picker and rule scope list show channel photos too.

### 5.10 Search, dates and shared media

Search, date jumps and shared media run over all of a feed's sources as one merged list and obey the feed's filter.

- **Home search.** `searchAllChannels` asks TDLib's `searchMessages` without a chat list, so the main list and the archive are both searched, with its channel filter; it pages with the token TDLib returns and drops anything that is not a channel of this account. Results use the rows of the feed search; a tap opens that channel's timeline at the post. The home screen loads the archived channels when the search opens, for the names and photos of their results and to open them.
- **Filter chips.** `SearchFilterChips` sits under both search fields and maps to `HistoryFilter`: Everything, Media, Links, Files, Music, Voice. A chip with no words is a search of its own. With a kind chosen `SearchResults._byKind` lists the results as the shared media tabs do (`MediaTile` in a grid whose viewer pages through everything found, `FileRow`, `LinkRow`, `MediaRow`, each row under its channel's name); a long press on an item opens its post.
- **Typed dates.** `dateSpans` (`feeds/search_dates.dart`) reads the home search's words as dates, after the official `FiltersView.fillTipDates`: today, yesterday, a weekday, a year from 2013 on, a month, a day and a month in words or digits, with or without a year; month and weekday names come from `intl` for the app's language and for English, and nothing lies in the future. Each `DateSpan` is a chip; a picked one (`_pickDate`) empties the field and is sent as `minDate` and `maxDate` of `searchAllChannels`, which are TDLib's `min_date` and `max_date` of `searchMessages`. TDLib answers nothing when there are neither words nor a kind (`search_messages` returns an empty result for an empty query with an empty filter), so for a date alone `GlobalSearchSession` reads the channels one by one: a `FeedSearch` over every channel, the archived ones too, with a date window. With `maxDate` each source starts just past `messageIdByDate`, and a source ends at its first post older than `minDate`; `FeedSearch.totalCount` is -1 then, since Telegram's counts are of whole channels.
- **Writing in a thread.** `reply` takes `replyToId`, the comment that is answered (the thread's own message otherwise). `Comment.replyTo` (`CommentReply`: id, author, first words) is filled by `TdlibGateway._comment` with one `getMessage` per answered comment, kept for the session; a deleted one leaves only the id, drawn as "Deleted message". `Comment.reactions` come from the message's interaction info and are set with `react` on the discussion group's chat id. `Comment.sendState` is TDLib's `sending_state`. For the threads that are open the gateway turns TDLib's updates into two streams: `comments` carries new comments and every change of a known one (`updateMessageContent`, `updateMessageEdited`, `updateMessageInteractionInfo`, `updateMessageSendSucceeded`, `updateMessageSendFailed`), which `ThreadScreen` takes by id as a replacement or an addition; `commentsGone` carries deletions and the temporary id of a comment that was sent, which leaves when the sent one arrives. `editComment` is `editMessageText`, `deleteComments` is `deleteMessages` with `revoke`, `retryComment` is `resendMessages`. The screen offers Edit for own comments of words that are younger than 48 hours.
- **Who may write.** `discussion` reads the discussion group's `supergroup` and fills `Thread.write` (`ThreadWrite`): `joinNeeded` when the account has left and the group has `join_to_send_messages`, `restricted` when it is banned or restricted from sending or the group's default permissions forbid messages, `allowed` otherwise and whenever the group cannot be read. `Thread.slowModeWait` and `slowModeDelay` are `slow_mode_delay_expires_in` and `slow_mode_delay` of the full info, zero for admins. `ThreadScreen._writing` draws the field, or the reason in its place; the slow mode's wait is counted down by a timer and starts again after each comment that was sent, and an edit is not held back by it.
- **Recent searches.** `RecentSearches` (`search.recent` in `settings`) keeps the last ten queries of the whole app, newest first and without repeats. A query is kept when one of its results is opened, not when it is typed. `remove` takes one out (the cross of its row), `clear` all of them, after `SearchResults._askToClear` has asked. The search bars of the home screen and of a timeline offer them while nothing is typed and can clear them; the search in comments has none.
- **Comment search.** `searchThread` calls `searchChatMessages` scoped to the thread, so Telegram finds a comment far above without the app paging the whole thread; it returns a `CommentPage` with Telegram's count of the matches and where the next page starts. `_ThreadSearch` (`feeds/thread_screen.dart`) keeps the pages of one query. The flow is the timeline's: sent words open the newest match (`_openResult`), `SearchStepper` takes the place of the comment field, its arrows open the neighbouring results, fetching further pages as they are reached, and "Show as list" covers the thread, which stays mounted off stage, with the results. `CommentBubble.highlight` marks the found words.
- **Landing on a comment.** `_jumpToComment` serves search results and reply quotes. A comment that is not loaded is fetched with its neighbours by `threadAround` (`getMessageThreadHistory` from that comment with a negative offset: up to `newer` comments after it, itself, and `older` before it). Where they touch the loaded comments the two are joined; otherwise the thread is rebuilt around the comment and `_atNewest` is false: the list then ends before the discussion does, `_onPositions` fetches the next 30 newer comments (`_loadNewer`, again `threadAround`) whenever the lower end is near and keeps the screen where it is (`_heldRow`), comments that arrive are only counted, and sending a comment reloads the newest page (`_showNewest`). `_landing` holds `_loadNewer` back until the list stands on the comment.
- **Engine.** Search and the media tabs share `FeedSearch` (package `core`): the merge of `FeedTimeline` over `searchHistory` instead of `history`, with a buffer and a next offset per source, `(date desc, chatId, messageId desc)`, and `loadMore()` for the next page. Albums are not collapsed: a result row or a media tile is one message. A media tab is the same search with an empty query and a `HistoryFilter` (photo and video, document, link, audio, voice), which the gateway turns into TDLib's `SearchMessagesFilter`.
- **Counts.** Telegram's `total_count` per source is summed into `FeedSearch.totalCount`. It counts what the server matched, so with a filter it is an upper bound; once the search is exhausted the number of results is exact.
- **In the timeline.** The magnifier turns the app bar of `TimelineScreen` into a search field (`SearchResults`, `SearchResultTile`, `SearchStepper` in `feeds/timeline_search.dart`). Nothing is searched while words are typed. Sending them (`onSubmitted`) runs a `SearchSession` and opens its first result (`_openResult(0)`): the timeline jumps to the newest match, and `SearchStepper` under it steps through the matches with "3 of 47". Its "Show as list" covers the timeline with `SearchResults`, each row naming its channel and marking every word of the query (`foundRanges`, which joins places that overlap), and "Show as chat" uncovers it; a tap on a row opens that result. A filter chip and a tapped hashtag start their search as a list (`_startSearch(asList: true)`). Back (`_backFromSearch`) leaves the list when a result is open under it and closes the search otherwise. While the search is open `TimelineView.highlight` carries the query to the rows (`_RowInputs.highlight`, `PostCard.highlight`), and `FormattedText` paints the places `foundRanges` finds, every word of the query whatever its case, in the selection colour. Before anything is typed the words searched for last cover the timeline.
- **Jumping to a post.** `TimelineViewState.jumpToPost` scrolls to a post that is loaded (`_scrollToLoaded`), as `scrollToMessageId` of the official app does: animated over 250 ms, the row in the middle of the list or with its top at the top when it is taller (`_centredTop`, the official `getScrollOffsetForMessage`), less the pinned bar. The list is aligned by the bottom edge of the row above the post, which is the post's top edge; a row that is not laid out has no height yet, so its top goes a quarter down the screen first and the row is centred once it stands there. A row so near the newest post that centring would leave the list empty under it sends the list to its end instead. The row is tinted for one second from the end of the scroll, and a drag of the list ends the tint. A post that is not loaded rebuilds the timeline anchored at that post: the post itself for its own channel, `anchorsForDate` for the others; the list opens with the post's top a quarter down and centres it at its first layout. A link to a post of a channel of the timeline (`_openTelegramLink`) takes the same path and leaves the post it stood in as the place the corner button returns to; an unloaded post of a feed with several channels or a filter opens the channel's own timeline, since the link tells no date to anchor the other channels at and the filter may hide the post. One page of newer posts loads straight away, so the post stands among its neighbours. `FeedTimeline.loadNewer` (gateway `historyAfter`, TDLib's negative offset) adds more as the reader scrolls down; every row it adds moves the indices, so the list is jumped back to where the reader was. While the timeline is jumped, new posts wait on the badge, the remembered position is left alone, and the corner button rebuilds the live timeline at its newest post. A rebuilt list keeps the scroll position of the old one, so a later opening also jumps explicitly; `initialScrollIndex` counts only for the first build.
- **Dates.** `anchorsForDate` asks every source for the newest post sent no later than the chosen day (`getChatMessageByDate`; a 404 means the channel has nothing that old and contributes nothing there). The calendar (`CalendarScreen`, `feeds/calendar_screen.dart`) opens from the search bar or from a day pill (`TimelineViewState.pickDate`) and pops with the day that was tapped, which `jumpToDate` opens. It lists the months from this one back to August 2013 in a reversed list, so this month is at the bottom, and opens at the month of the pill. Each day with a photo or a video shows that post's smallest picture in a circle behind its number: `mediaCalendar(chatId, fromMessageId)` is TDLib's `getChatMessageCalendar` with `searchMessagesFilterPhotoAndVideo`, one post per day, newest first, in pages. The screen reads the pages of every channel of the timeline, four channels at a time, down to the oldest month the list has built, and keeps the newest post of each day; a page that tells no older day ends a channel. The timeline pages down to the day before (at most 300 rows) and settles on the first post of the chosen day, or on the closest older post for a day without posts. A date before everything the sources have is reported as such.
- **Button to the newest posts.** It carries the unread counter and leaves a jumped timeline (section 5.4).
- **Channel info.** A channel's title in the timeline opens `ChannelInfoScreen`: photo, name, subscribers (the whole number, grouped by `NumberFormat.decimalPattern`), description, the link (`@username` for a public channel, the invite link for a private one; a tap hands it to the share sheet), the channel's QR code (`qr_flutter`), similar channels (`similarChannels`, TDLib's suggestions; a tap opens one in the official app) and the shared media tabs. It has no mute and no leave. `ChannelInfo.photos` is every photo the channel has had, the current one first: `channelInfo` reads them from the history (`searchChatMessages` with `searchMessagesFilterChatPhoto`, whose service messages carry a `chatPhoto`). A tap on the small photo opens them in the media viewer; a pull down at the top (an `OverscrollNotification` of a drag, caught around `SharedMediaTabs`) replaces the small header by `_PhotoGallery`, a square `PageView` of them with the name over its lower edge and a mark per photo along the upper one, and its arrow brings the small photo back and the screen to its top. `ChannelInfo.descriptionEntities` are what TDLib's `getTextEntities` finds in the description, which is plain text; `FormattedText` draws and opens them as in a post.
- **Shared media tabs** (`SharedMediaTabs`, `feeds/shared_media.dart`): Media, Files, Links, Music, Voice and GIFs (`sharedMediaKinds`), each a `FeedSearch`, paged as it scrolls. Which kinds get a tab is asked first: `mediaCounts` (TDLib's `getChatMessageCount` per kind) summed over the channels; a kind with none has no tab, a kind that could not be counted keeps it. Media is a grid of cropped pictures with the length on videos; a tap opens the viewer over everything the tab has loaded. Its button in the tab bar chooses photos, videos or both (`HistoryFilter.photo`, `.video`, `.photoAndVideo`; one is always on), and GIFs (`HistoryFilter.animation`, which Telegram keeps apart from videos) are a grid of their own. A grid's columns are `mediaGridColumns`, a notifier shared by every grid while the app runs: a pinch moves it between two and nine, and while two fingers are down the grid does not scroll. `_DateScroller` is the handle along a grid's edge: it follows the grid's `ScrollPosition`, a drag jumps it through what is loaded and shows the month of the item on top (found from the offset, since the cells are square), and the page that loads at the end extends it. Files, Links and Music have a search field, whose words start a new `FeedSearch` after 300 ms. A long press on an item opens a menu with "Show in chat" (`onShowInChat`, given by the screen that knows the timeline: the channel's timeline jumps there, the home screen and the feed's info open one at that post). Files name the file before download and carry the timeline's download control. Links open in the browser. Music and Voice use the timeline's audio players.
- **Feed info.** `FeedEditorScreen` is the feed's info screen: a "Channels" tab with the sources, the filter row and the picker, a "Rules" tab with the feed's rules (`RuleList`) and a button for a new one, and the same five media tabs over all of the feed's channels, with the feed's filter. A tab's search starts over when the channels or the filter change. The feed's title in the timeline opens it.

### 5.11 Settings

`SettingsScreen` holds the profile (`AccountHeader`: photo, name, username, phone, bio, Telegram ID) and one row per screen, and no setting of its own. Log out is in the app bar's menu. The rows, in order:

- The other accounts (`AccountRows`, `settings/account_rows.dart`) and Saved Messages, under the profile.

### 5.12 Sound

`AudioSessions` (`media/audio_session.dart`) is the app's one audio player: voice messages and music play in it, so only one sound is heard at a time and a post that scrolls away keeps playing. A track comes with the queue it stands in (`AudioItem`s, oldest first): `TimelineView` hands its rows an `AudioQueue`, the voice messages or the music of the posts it holds, each with a `load` that downloads the file when it is asked for. When a file has played to its end (`AudioEngine.completed`) the session plays the next entry of the queue, and with none left it stops, so the bar goes and the row is a play button again. Music follows `AudioSessions.repeat` (off, the whole list, one piece) and `shuffle` (a shuffled order of the queue with the playing piece first); voice messages follow neither. `next` and `previous` walk the same order; `previous` goes to the start of a piece that has played more than three seconds. `AudioView` draws the player in the row whose file is the session's track, whoever started it, and starts playing only on its own tap. A track outside a timeline (shared media, search results, comments) has no queue and plays alone. A video in the viewer calls `pauseForVideo`, which remembers that it paused a playing track; the viewer on closing, and the mini player on closing for good, call `resumeAfterVideo`, which plays it on unless the track was paused, played or stopped by hand meanwhile. It sits behind an `AudioEngine` interface (`just_audio` in the app, a fake in the tests) and holds the track, whether it plays, the position and the speed (1×, 1.5×, 2×) as notifiers, which the row in the post and the player bar both follow. `StatusBannerHost` (`widgets/status_banner.dart`), which sits in the app's `builder`, shows the `AudioBar` in the `ScaffoldMessenger`'s material banner, so it stands under the header of every screen while something plays and the sound survives scrolling away or opening another screen. A messenger shows one banner at a time, so the bar and the line about reading aloud or the pause are one banner, the bar on top, shown again only when what it holds changes. A tap on the bar's words calls `AudioItem.onShow` for a voice message (the timeline pops to its own route and jumps to the post; nothing happens once that timeline is gone) and opens `AudioPlayerSheet` for music: the seek bar, previous, play and next, repeat and shuffle, the speed, and the queue, newest on top, where a tap calls `playItem`. When the music stops the sheet removes its own route, once. `AudioSpeedButton`, in the bar, the rows and the player, goes round `AudioSessions.speeds` on a tap and opens a menu with a `SpeedSlider` (0.5× to 2×) and four speeds on a long press. The session keeps one speed for voice messages and one for music and applies the track's own when it opens it.

`NowPlaying` (`media/now_playing.dart`, started by `PipHost`) tells Android what the session plays over `tf/nowPlaying`: `show` with the title and artist (`AudioItem.title` and `artist`: the piece and its performer, or "Voice message" and the channel; the label for a track without a queue), whether it plays, the position, length and speed, whether there are other pieces, and the words of the buttons; `hide` when nothing is open. It sends when the track, the playing state, the speed or an error changes, and when the position is more than 1.5 seconds from where Android counts it (a seek); a track that is being opened (`AudioSessions.starting`) counts as playing, so no pause shows between two tracks. `NowPlaying.kt` holds a `MediaSession` with that metadata and playback state and posts a `MediaStyle` notification on channel `playback` (`LOW`, public on the lock screen) with previous, play or pause, and next; Android draws the lock screen's player and the seek bar from the session. The session's callbacks (headset buttons, the system's player) and the notification's buttons (`PlaybackReceiver`) come back as `play`, `pause`, `next`, `previous`, `seek` and `stop`, which call the session. While the track plays, `PlaybackService` (foreground service type `mediaPlayback`) holds the notification, so the process keeps playing in the background; on a pause the service leaves the foreground with the notification detached and stops, so the notification can be swiped away, and its delete intent sends `stop`. A foreground start that Android refuses to a background app is caught, and the notification is posted without the service. When the UI engine goes (`cleanUpFlutterEngine`), the session, the service and the notification go with it.

### 5.13 Media viewer

The viewer (`MediaViewerScreen`) pages through every picture and video the timeline holds, not only one post's album. The card asks the timeline for its media (`_viewerMedia`, newest first down to each album's first picture, the feed's filter already applied because it walks the loaded rows) and opens at the tapped one. With `newestFirst` the pages run the other way round, older on the left as in the official app: a swipe to the left goes forward in time, and "N of M" and the picture's hero tag count from the album's first picture. Two pages from the older end it calls `onNeedOlder`, which pages the timeline and hands the list back grown; a list that does not grow is the end. A `ViewerDetail` per item carries the channel, the day and the caption, which the top bar and the band at the bottom show. The viewer's Save to Saved Messages acts on the post the picture belongs to (`onSave` by index).

A picture grows out of the row it was tapped in and shrinks back into it: both sides name it the same way (`mediaHeroTag`, the post and the picture's place in it), the row from the post it draws and the viewer from the `ViewerDetail` it was handed, so neither has to be told. Only the page in front carries the name, since two heroes of one name on a route are not allowed, and a video carries it only while it is still a poster, so a running player is never handed to the flight. A picture the caller says nothing about, a channel's own photo, has no name and fades as before.

The top bar (`ViewerTopBar`) holds the back arrow, the channel and the day on one line each, and then the buttons: on a video the download ring while a download runs and the picture-in-picture button, then Share and the three dots. Everything else is behind the dots (`ViewerMenu`, dark whatever theme the app is in): Download or Cancel download with the file's size, Show in chat, Open in…, Save to Saved Messages, Save to gallery. "Show in chat" is `ViewerDetail.onShowInChat`, which the caller that has a timeline fills (the timeline jumps to the post, the shared media and the search results open it); the viewer closes first. "Open in…" hands the file to Android's chooser through `openDownloadedFile`, a video only once it is whole on the phone, and is absent for protected content. `ViewerDetail.entities` carries the caption's formatting, which `ViewerCaption` draws with `FormattedText` under a dark theme; a tapped link closes the viewer and goes to `ViewerDetail.onOpenLink`, or to the browser where the caller gave none. A single tap within 45 px of a side edge (an eighth of the width where that is less) and below the top bar turns the page (`_edgeTap`, asked by `ZoomablePhoto` and `VideoStage` before they treat the tap as their own); at the first and last page it is an ordinary tap. The lines are built when the menu opens, so each says what it does at that moment.

Share hands the picture or the video itself to the system sheet (`share`, `share_plus` with the file), not the post's words. A video is shared only once the whole file is in Telegram's cache — the viewer asks TDLib for the file's downloaded prefix, because the post's `FileRef` is as old as the post — and otherwise says "Download the video first to share it." with a Download button on the snackbar. A picture is downloaded first, as Save to gallery does. Sharing a post's words and its link is the timeline's Share, in the row's menu and in the selection bar.

The top bar and the caption go together: a tap on a picture puts both away and brings them back, and on a video they follow the player's controls, which also hide by themselves three seconds into playing, unless the phone reports accessible navigation (a screen reader, or a UI test working through the same service): then they stay until tapped away. The caption (`ViewerCaption`) stands above the player's bar and scrolls inside at most a third of the screen.

"Save to gallery" goes through the `tf/gallery` method channel: the Kotlin side inserts the file into `MediaStore` under `Pictures/TG Feed` or `Movies/TG Feed` (no permission needed for the app's own file on Android 10 and later) and answers with its uri. The same call with `to: downloads` or `to: music` (`SaveTo`) puts a document into `Download/TG Feed` and a music file into `Music/TG Feed`. The file is downloaded first when the cache does not have it.

### 5.14 Automatic downloads and autoplay

Automatic downloads and autoplay are one setting. `AutoDownloadScope` (`media/auto_download.dart`) sits above the navigator and hands every media widget an `AutoDownloadPolicy`: the `DownloadPreset` of the connection the phone is on, and the two Autoplay switches.

- **Connections.** Mobile data, Wi-Fi and roaming, each with its own preset (`media.download.mobile|wifi|roaming`, JSON, synced like every `media.*` setting). The connection comes from the `tf/network` method channel: metered Wi-Fi counts as mobile data, cellular without `NET_CAPABILITY_NOT_ROAMING` as roaming. It is read again when the app resumes.
- **Presets** follow the official app: a switch for the whole connection, photos (no size limit), videos up to a size, files up to a size, and "Preload larger videos". Telegram's three are built in: Low (photos only), Medium (videos to 10 MB, files to 1 MB) and High (videos to 15 MB, files to 3 MB). A fresh install has Medium on mobile data, High on Wi-Fi and Low while roaming. GIFs and round video messages count as videos; music counts as files. A voice message follows the connection's switch alone (`AutoDownloadPolicy.voice`): up to 512 KB it loads whatever the files switch and its limit say. A size limit is set on a slider without steps (`downloadSizeAt`, `downloadSizeProgress` in `settings/data_storage_screen.dart`), whose quarters end at 1 MB, 10 MB, 100 MB and 2000 MB as the official app's do.
- **Behaviour.** A photo within the preset loads as soon as its row is built. A video within the limit downloads whole through `VideoDownloads.start(auto: true)`, so its pill shows the progress; a download the user stops by hand does not restart by itself in this run. A larger video with preloading on, where the video limit is over 2 MB, gets its first 2 MB (`downloadFrom` with a `limit`, TDLib's `downloadFile` limit), so a tap plays it at once. A file within the limit starts in its row; a voice message or a song loads ahead without playing. The preloading switch rests while the limit in its sheet is 2 MB or less. A size TDLib has not reported yet waits for a tap.
- **Autoplay** follows the download: a video autoplays when it loads by itself and its Autoplay switch (GIFs, videos) is on. Autoplay has no length or size limit of its own.
- Until the settings and the connection are known the policy is `unknown`, nothing starts, and a spinner stands in; when the policy then allows it, the row starts at once. Without a scope (widget tests of a single view) only pictures load.

### 5.15 Telegram links

`telegramTargetOf` (package `core`) parses `t.me/<name>`, `t.me/<name>/<post>`, `t.me/c/<internal id>/<post>`, `tg://resolve` and `tg://privatepost`, with the post as a TDLib message id. A link in a post that names a channel the account follows opens that channel's timeline in the app, at the post. Invite links, sticker sets and web pages go to `launchFirst` and the system. The app does not register as a handler for t.me links from other apps.

`launchFirst` tries each candidate link in turn and survives the exception `url_launcher` throws for `tg://` when no app handles it, so Open in Telegram falls back from `tg://privatepost` to `t.me`. `telegramPostUri` builds `https://t.me/<user>/<id>` for public channels and `tg://privatepost` plus a `t.me/c` fallback for private ones. Share puts the `t.me` link into the system share sheet (`share_plus`); Copy link uses the clipboard.

### 5.16 Interface language

The interface is in English and Ukrainian, through Flutter's `gen_l10n`.

- **Strings.** `app/lib/l10n/app_en.arb` is the template and `app_uk.arb` its translation, with ICU plurals (Ukrainian `one`, `few`, `many`, `other`) and selects. `flutter pub get` and every build generate `AppLocalizations` beside them (`l10n.yaml`). Widgets read `context.l10n` (`l10n/l10n.dart`), which falls back to English where no localizations are in scope, as in widget tests that build a bare `MaterialApp`. `language_test.dart` checks that every English key has its Ukrainian one.
- **Wording.** Ukrainian follows the official Telegram Android app's Ukrainian strings (translations.telegram.org): «допис» for a post, «Збережене» for Saved Messages, the apostrophe ʼ. App and brand names, Telegram's own error texts, size units (KB, MB) and the rule syntax (AND, OR, NOT) stay as they are.
- **Choice.** `SettingKeys.language` (`interface.language`: `system`, `en` or `uk`; not synced) sets `MaterialApp.locale`; `system` leaves it null, so Flutter resolves the phone's languages against the two the app has, English when it has neither (`AppLanguage.ofPhone`). The Language row in Settings opens `LanguageScreen`: System, which names the language the phone leads to, then each language under its own name.
- **Dates.** Day labels use intl's `DateFormat` with patterns from the ARB files (`postDayPattern`: "October 2", «2 жовтня»); `GlobalMaterialLocalizations` loads the Ukrainian date symbols. English formats with `en_US`, which intl has without loading.
- **Packages carry data, the app words it.** Packages stay free of interface text: the gateway hands over the media of a post without text (`Channel.lastMessageMedia`, `ReplyTarget.media`) instead of a label, `mediaLabel` and `postLabel` take `MediaWords`, and errors carry a kind (`RuleSyntaxError.problem`, `SemanticException.problem`, `SyncException.problem`) beside an English `message` for logs. Google sign-in and Drive failures are a `DriveException` with its `DriveFailure`; the sync status holds a `SyncFailure`, which the sync screen words, and the AI failure note (`ai.lastError`) stores the problem beside the message. Saved Messages, which TDLib names in English, gets its title from the app (`Channel.withTitle`).
- **Service.** The service host has no widget tree; it takes its strings from `AppLanguage.strings` (the setting, else the phone's languages) when it starts. `CoreHost` sends `{'language': code}` when the setting or the phone's language changes; the service then names the permanent notification, its buttons and every notification channel again (Android renames an existing channel when it is created again with the same id), and later rule notifications use the new words.

### 5.17 Storage usage and the cache

- **By kind.** `storageByKind` asks TDLib's `getStorageStatistics` (a walk over the files, slower than `getStorageStatisticsFast`) and sums the chats into one `StorageSlice` per `StorageKind`: photos, videos (with GIFs and round video messages), files, music, voice, stickers, profile photos and other (thumbnails, wallpapers, notification sounds, unknown). Kinds without files are left out; the largest comes first. `storageKindOf` and `fileTypesOf` (`mapping.dart`) map between the kinds and TDLib's file types.
- **Screen** (`settings/storage_usage_screen.dart`): `StorageChart` draws a ring with an arc per ticked kind and the size of what is ticked in the middle; each kind is a `CheckboxListTile` in the kind's colour (`storageKindColor`) with its share and size. The button clears the ticked kinds (`clearCache(kinds:)`, or the whole cache when every kind is ticked) after a question, then reads the numbers again. The database size is a row of its own and cannot be cleared.
- **Automatic removal.** `CacheLimits` (`media/cache_limits.dart`) holds the choices and defaults: `cache.keepSeconds` (a day, two days, a week, a month or 0 for never; a week when nothing is stored) and `cache.maxBytes` (2, 5, 16 or 32 GB, or 0 for no limit, which is the default). Neither syncs. `CacheLimits.follow`, started by `CoreHost`, calls `setCacheLimits` when the account is logged in and whenever one of the two changes.
- **TDLib's cleaner.** `setCacheLimits` sets TDLib's options `storage_max_time_from_last_access` (seconds), `storage_max_files_size` (kilobytes), `storage_max_file_count` (the largest value, since TDLib would otherwise stop at 40000 files) and `use_storage_optimizer` (false when there is neither a time nor a size). TDLib keeps options in its database, so the service host runs with the same limits without setting them. With the optimizer on, TDLib cleans about once a day: it removes files whose last access, or last change where that is later, is older than the time, then the longest unused ones while the cache is over the size. Files changed in the last hour, and thumbnails, profile photos, stickers, wallpapers and notification sounds, are left alone by that cleaning.

## 6. Rules and notifications

### 6.1 Rule model

```
rules (id, name, enabled, feed_id, scope_chat_id?,
       condition_json, priority {silent, normal, urgent}, read_aloud,
       schedule_json?, created_at, semantic_prompt?, sync_id, updated_at)
```

Every rule belongs to a feed (`feed_id`) and watches all of its channels, or the one in `scope_chat_id`. Deleting the feed deletes its rules; removing a channel from a feed deletes the feed's rules for that channel. Both leave tombstones for sync.

The rules list (`RuleList`, `rules/rules_screen.dart`) shows the rules of one feed on the Rules tab of its info screen, which the feed row's menu also opens, and all rules under a header per feed behind the Rules button of the home screen (`RulesScreen`). The editor (`RuleEditorScreen`) picks the feed, preset to the feed it was opened from, and then one of that feed's channels or all of them.

Condition AST (package `rules`):

```
Expr = And(List<Expr>) | Or(List<Expr>) | Not(Expr) | Term
Term = { text, wholeWord: bool, caseSensitive: bool }     // multi-word text = phrase match
Schedule = { weekdays: Set<1..7>, from: "HH:mm", to: "HH:mm" }   // local time, may wrap midnight
```

The editor is a visual builder (groups of terms with AND/OR, NOT per term) plus a text form `("bitcoin" OR btc) AND NOT airdrop` that parses to the same AST (`RuleParser`). Both are `ConditionEditor` over a `ConditionController` (`rules/condition_editor.dart`), which a feed's filter uses for its words as well (section 5.8). Terms are bare words or quoted phrases, whole-word and case-insensitive by default; prefix `~` for substring match and `=` for case-sensitive. `AND` binds tighter than `OR`, `NOT` tightest. `RuleParser.format` renders the AST back. Whole-word matching is Unicode-aware: Dart's `\b` is ASCII-only, so boundaries are `(?<![\p{L}\p{N}_])…(?![\p{L}\p{N}_])` with `unicode: true`. CJK text has no inner word boundaries, so `~` is the match to use there. Case-insensitive matching uses the regex engine's Unicode case folding, which covers Cyrillic.

A rule with no condition (`And([])`, which every post satisfies) notifies about every post of its channels. The editor saves it when both keyword editors are left empty, and the rules list shows it as "every post". Scope, priority, schedule, read-aloud and the feed-filter check (section 5.8) apply to it like any other rule. It also matches a post with no text at all; its notification and the dry run show what the post carries instead ("Photo", "Video", the file's name; `postLabel` in `core`). An AI rule never counts as one: there is nothing to send to the model.

### 6.2 Evaluation

`RuleEngine` runs in the core isolate and reads the rules and the feeds, each with its channels and filter (`RuleFeed`), from the database whenever the host signals a change (`refresh`). On every new post of a channel in some feed:

1. Extract the text: message text or media caption, formatting flattened. Nothing else is matched (no forward origin, no URLs beyond their visible text). A post without text only reaches rules with no condition (section 6.1).
2. Candidate rules are the enabled rules of the feeds that hold the channel, for the whole feed or for this channel, whose feed shows the post (section 5.8), filtered by schedule against the local clock.
3. Evaluate each condition and collect matches.
4. If none match, stop. Otherwise priority is the maximum over the matches and read-aloud is true if any match asks for it.
5. Send a `MatchEvent` to the service host, which shows the notification (section 6.3) and, if read-aloud is set, queues the post for speech (section 7).

An album is one post. Its parts arrive as messages of their own, so `RuleEngine.attach` holds the parts of an album (`Post.albumId`) until none has come for a second (`albumWait`) and `evaluateAlbum` judges them together: the captions joined are its words, a rule's feed shows it when `FeedFilter.shownParts` leaves any part, and the match names the part with the caption, or the first part. The notification of an album without a caption says "Album".

Edited posts are not evaluated again. A deleted post cancels its notification.

The pause stops evaluation: `CoreServer.setPaused` detaches the engine from the gateway's post events, so nothing matches, notifies or is read aloud. The core keeps it in the device-local setting `rules.paused` (`onPaused`) and starts paused when it says so. It is switched from the home screen's header (`PauseButton`), from the banner's Resume and from the Pause and Resume actions of the service notification; the core tells every client (`CoreStream.paused`). On a pause the service host stops read-aloud and clears its queue (`TtsService.stopAll`). While paused, `StatusBannerHost` shows a banner with Resume under the header of every screen; a post read aloud (Listen still reads) takes its place until the queue is empty.

### 6.3 Notifications

`RuleAlerts` (`service/rule_alerts.dart`) turns the core's matches into notifications and read-aloud. It holds the `Notifier`, the `TtsService`, the semantic gate and the port for notification actions, and lives beside the core: `CoreServiceHandler` runs it in the service host; with background watching off `CoreHost` runs it in the UI isolate, so rules notify and read aloud while the app's process is alive. `MainActivity` gives its engine the `tf/readAloudKeys` channel for that case.

`Notifier` uses `flutter_local_notifications` with one Android notification channel per priority:

| Priority | Android channel importance | Behaviour |
|---|---|---|
| silent | LOW | In the shade, no sound, no heads-up |
| normal | HIGH | Heads-up, with the sound and vibration chosen in Settings. The channel id is `posts_normal_popup`; the notifier deletes a `posts_normal` channel, which does not pop up, because Android keeps the importance a channel was created with |
| urgent | HIGH + `bypassDnd` | Heads-up, with the sound and vibration chosen in Settings. Bypassing Do Not Disturb needs notification-policy access. The manifest declares `ACCESS_NOTIFICATION_POLICY`, without which Android leaves the app out of its Do Not Disturb access list, and the rule editor opens that list when urgent is picked. Android fixes a channel's DND bypass at creation, so the notifier posts on `posts_urgent` until access exists and then creates `posts_urgent_dnd` (and deletes the other); it checks before every urgent notification |

While the app is on screen, normal and urgent posts of the timeline in front go on in-app channels at `DEFAULT` importance with the same sound, vibration and Do Not Disturb bypass (`posts_normal_inapp`, `posts_urgent_inapp`, `posts_urgent_inapp_dnd`): they sound but do not pop up over the timeline they have just appeared in. Posts of any other channel pop up over the app. A `TimelineScreen` that is its route's current screen tells `Viewing` (`host/viewing.dart`) the channels it reads, a feed's sources or the one channel, and takes them back when another screen covers it or it is closed; `Viewing.chats` holds those of the timeline on top. `CoreHost` sends the service `appOpenMessage(open, unlocked:, viewing:)` when the app's lifecycle state or `Viewing.chats` changes (or sets them on its own `RuleAlerts`), and `Notifier.appOpen` with `Notifier.viewing` picks the channels; only `resumed` counts as on screen, so in picture-in-picture every post pops up.

Sound and vibration are chosen per normal and urgent rules: a sound from Android's own picker (`tf/notifications.pickSound`, an activity result) and a vibration switch; silent rules stay silent. Android fixes a channel's sound when the channel is created, so the choice is part of the channel id: the default sound uses the plain ids (`posts_normal_popup`, `posts_urgent` and their in-app counterparts), any other choice adds a suffix derived from it, and channels of earlier choices are deleted, so the system settings show one row per priority and place. The service host reads these settings when it starts; `CoreHost` watches them and sends the service `sounds`, on which `Notifier.setSounds` makes the channels of the new choice and deletes the old ones, so a change applies at once. The sound row shows the ringtone's own title (`tf/notifications.soundTitle`).

Notification texts, actions and channel names are in the interface language (section 5.16). A channel has one notification (`NotificationPlan.idForChat`), a `MessagingStyle` conversation: the sender is the channel, with its photo as the person's icon and the large icon, and every matched post still listed is a message with the post's words (`NotificationPlan.bodyOf`: one line, cut at 240 letters, a caption marked with 🖼, 📹, 🎬 or 📎 by `markOf`, a post without words named by what it carries) and the post's time. A `NotificationPlan` is one such line; `Notifier` keeps the lines of each channel, oldest first and at most `maxListed` (25, what Android keeps of a conversation), and posts the whole notification again whenever they change. Android draws a message's picture in place of its words and shows only the lines that fit, so only the newest post carries its picture, as a second message under its words. The rule of the newest post is the conversation's title, which Android shows beside the app's name (it shows no sub-text for a conversation). The actions are **Open in Telegram** and **Listen** (**Stop** while one of the listed posts is read or waits to be read); the one that changes comes last, so the other never moves. The payload is that of the oldest listed post, so a tap, and Open in Telegram, open that one, in the feed of the rule that decided (the first of the highest priority, `MatchEvent.feedId`); in the first feed that holds the channel when that feed is gone.

`Notifier.show` adds a line and posts the notification on the Android channel of the post's priority with `onlyAlertOnce` off, so it sounds and pops up again. A post of a silent rule, and one that is held quiet, is added with `onlyAlertOnce` on and leaves the notification on the channel it is on; such a post that starts a notification puts it on the silent channel. Everything that changes a notification runs one after the other (`_inTurn`). Before each change the notifier asks `getActiveNotifications` and forgets the channels whose notification Android no longer shows (one posted within the last two seconds counts, as Android may not list it yet), so a notification that was swiped away or opened starts a new list. The lists are kept in `notifications_listed.json` in the app's support directory (`ListedStore`), written after every change and read by `init`, so a restart of the host goes on with the notifications Android still shows.

Listen and Stop leave the notification in place. `TtsService.readingChanges` reports the posts being read or waiting, and `Notifier.setReading` posts again the notifications whose button has to change, with `onlyAlertOnce`, so nothing sounds. The service host hears of the buttons, swipes and taps on its port (`notificationActionEntryPoint`; the app reports a tap and Open in Telegram as `notificationTapped`). Listen queues the listed posts that `RuleAlerts` has not queued before (`_spoken`), oldest first and ahead of what waits, and all of them when every one was; Stop stops every listed post (`TtsService.stop`). A swipe and Clear all (`dismissIsolate: background`, a delete intent, reported as `notificationDismissed`) stop the listed posts and `Notifier.forget` the list; a tap forgets it too. A post that is read, here or in the official app (`readUpdates`, `Notifier.cancelRead` up to the read position), or deleted (`Notifier.cancel`) leaves the list; the notification is posted again without it, and cancelled with its last line.

Every notification names its small icon, `ic_stat_feed` (a white glyph on transparency that Android tints). The plugin keeps its default icon in shared preferences, where the isolate that initialises last would decide it, so no notification relies on the default. The service's notification names the icon on every update, because Android restores a running foreground service with the content saved when it was started.

Android 13 and later require `POST_NOTIFICATIONS`. `CoreHost` does **not** ask for it: its start runs before the login screen, on a blank spinner, and Android grants that ask once, so a reflexive refusal there would silence every rule for good. The service starts without it (its own notification is simply not shown) and the app asks where it can give a reason: when a rule is saved (`NotificationPermissionAsk`). The banner on Notifications and sounds opens Android's own page for the app's notifications.

`Notifier.show` lets one chat sound at most `soundLimit` (2) times within `soundWindow` (three minutes): it keeps when each chat's notifications sounded, and a post beyond the limit is added as a quiet line (`NotificationPlan.quiet`), without a sound and without a pop-up whatever its rule's priority. Posts of silent rules do not count. `RuleAlerts` hands a `PostEdited` to `Notifier.updateBody`: where the post is still listed its line says the new words (`NotificationPlan.bodyOf`) and the notification is posted again without a sound; rules are not evaluated again.

A match made while the app has a lock (`AppLock.enabled`, read from the keystore by the host the alerts run in; a keystore that cannot be read counts as a lock) and the app is not on screen and past its lock becomes a hidden line (`NotificationPlan.hidden`): sent by the app's name, "New post", no rule, no pictures, and a payload that still names the post for the tap. A notification that lists a hidden line has no buttons; it is titled by the channel only when it also lists a post that was shown openly. `LockGate` publishes whether the lock screen is up in `AppLock.locked` (true until it has looked), `CoreHost` sends it with the lifecycle as `appOpenMessage(open, unlocked:)`, and `RuleAlerts.unlocked` holds it. An edit does not uncover a hidden line.

`NotificationPictures` (`service/notification_pictures.dart`) finds the pictures of a line before it is shown: the channel's photo (from `myChannels`, kept for ten minutes) and, for a photo post that is not under a spoiler, the narrowest size of at least 600 pixels. Each is downloaded when it is not on the phone, and left out when it does not come within two seconds. `NotificationPictures.kt` (channel `tf/notificationPictures`, on the service's engine through `FeedApplication` and on the UI's through `MainActivity`) cuts the photo round into `cache/notify` ("avatar"; Android draws a conversation's icon as it is given) and returns a `FileProvider` content uri of the picture that the notification shade may read ("share").

### 6.4 AI semantic rules

A rule may carry a description of what the post should be about (`rules.semantic_prompt`). Its keyword condition is then an optional pre-filter; an empty one (`And([])`) lets every post of the rule's channels through, and the editor warns that all of them are sent to the model.

- The rule engine stays synchronous and offline: it applies scope, schedule and keywords only, and the `MatchEvent` lists every matched rule with its prompt (`MatchedRule`).
- The service host finishes the decision (`SemanticGate`): one request per post to an OpenAI-compatible `chat/completions` endpoint (`SemanticClient`) with all pending descriptions numbered; the model answers with the matching numbers or `NONE`. The request carries only `model` and `messages`, because reasoning models need room before their short answer and some providers reject a custom temperature or token cap. An empty answer counts as a failed check, not as `NONE`. `MatchEvent.withSemanticVerdicts` keeps the keyword rules and the confirmed semantic ones, and priority and read-aloud are recomputed from them.
- When the check cannot be done (no endpoint, offline, bad key, rate limit, unreadable answer), the semantic rules are skipped for that post. Keyword rules on the same post still fire and nothing is retried. The reason is stored in the `ai.lastError` setting, which the rules screen shows as a note until a check succeeds.
- Endpoint and model are settings (`ai.baseUrl`, `ai.model`). The API key is in the Android keystore through `flutter_secure_storage`, never in the database, and is deleted on logout. Plain `http://` endpoints are allowed, with a warning, for models on the user's own network.
- The rule editor's dry run sends the newest 8 posts that pass the keywords to the model.

## 7. Read aloud

- `TtsService` runs beside the core (section 6.3, `RuleAlerts`) and owns a single FIFO queue over a `Speaker` interface (`FlutterTtsSpeaker` in the app). The queue waits for each utterance to end, so a new item never interrupts a playing one, and it never drops items. A Listen request is spoken right after the current utterance instead of at the end of the queue; otherwise Listen and automatic read-aloud share one path. A post is queued before its notification is shown, so an automatically read post offers Stop from the start. Stop silences one post: the one being read stops and the next follows; a waiting one leaves the queue. Listen on a notification from before the service started asks the core for the post's text.
- The app plays the speech, not the engine. Android mutes audio played in the background by an app whose foreground service may not use audio while in use, and refuses it the audio focus (audio hardening: enforced from Android 17; Android 16 logs "AudioHardening … would be ignored" and "… would be muted"; `adb shell cmd audio set-enable-hardening 1` enforces it fully until the next reboot). A TTS engine plays in its own process, which has no such service. `FlutterTtsSpeaker` therefore takes the audio focus, has the engine write the speech into a WAV file in the temporary directory (`synthesizeToFile`) and plays that file with `just_audio` in the service host. The file is deleted after it was played.
- A foreground service may use audio while in use once it was started, or sent a `startService`, while the app was in use: from the app's screens or within a tap on one of its notifications (`mAllowWiu_noBinding` in `dumpsys activity services`, capability `A` in `dumpsys activity processes`). A service that Android starts after a reboot or an update has no such right. The service host posts its notification again (`FlutterForegroundTask.updateService`, a `startService`) every 60 seconds and before it handles Listen or Stop, so opening the app or tapping a notification gives the running service the right. When the focus is withheld and no call is on, the engine speaks by itself, which is heard right after a tap.
- The app's banner (`StatusBannerHost`, `widgets/status_banner.dart`): the service host sends `{'reading': ReadingNow}` (`service/reading_now.dart`: the post being read, its channel's title and how many posts wait) with `FlutterForegroundTask.sendDataToMain` after every change of the queue and whenever a post starts (`TtsService.readingChanges`, `TtsService.current`). `CoreHost` asks for it when it starts (`askReading`) and sends Stop (`stopReadingOf`, the post named) and Stop and clear queue (`clearReading`, `TtsService.stopAll`) with `sendDataToTask`. The banner is the root `ScaffoldMessenger`'s `MaterialBanner`, which every screen's `Scaffold` shows under its app bar. Its words follow the queue without the banner being shown again, and it waits under the full-screen viewer. With background watching off, `CoreHost` feeds the banner from its own `RuleAlerts` and stops posts through it.
- Volume down stops read-aloud and clears the queue (`TtsService.stopAll`), also with the screen off. Android gives the volume keys to the active media session that plays, and to a session that plays remotely, through a `VolumeProvider`, it hands the press instead of changing a stream's volume. While `TtsService.reading` is not empty, the service host holds such a session (`ReadAloudKeys`, `service/read_aloud_keys.dart`, over `tf/readAloudKeys` to `ReadAloudKeys.kt`) and releases it when the queue empties, so the keys work as usual otherwise. Its provider mirrors the media volume: volume down reports `stop` and leaves the volume alone, volume up raises the media volume (`ADJUST_RAISE`). The held session also receives media buttons: pause and stop report `stop`. Android's volume panel shows the session as a row of its own, with a cast icon, beside the media slider.
- flutter_tts answers neither `synthesizeToFile` nor `speak` when the engine fails or is stopped; `FlutterTtsSpeaker` ends the utterance from the error handler and from its own stop, so the queue moves on.
- Language: `google_mlkit_language_id` (on-device), or the "Language when unknown" setting when detection fails (default English). The language selects the user's voice for it, or the engine's default voice for that language.
- Text preparation (`prepareForSpeech`, package `core`): URLs become "link", whitespace collapses, emoji and formatting markers are dropped, "New post in <channel>" is prepended. Posts over the maximum length are cut at a sentence boundary with "… and more". These words are in the language of the voice when the app has it (English or Ukrainian), otherwise in the interface language (section 5.16), so one voice reads the whole utterance.
- Audio focus (`audio_session`, media usage, speech content): transient focus with ducking, taken for the first utterance and released when the queue drains. It is kept through an interruption, because regaining it is what ends the interruption. A transient loss (a phone call, another app's spoken prompt) pauses the queue and the interrupted item is spoken again afterwards; a loss that allows ducking (a notification sound) is left to Android, which ducks the speech; a permanent loss (another app starts playing) ends the post being read. While a call holds the focus (`AudioManager` mode other than normal), the queue waits and asks again every 5 seconds. `audio_session` keeps a refused request and answers later requests from it as granted, so a refused request is abandoned at once. No telephony permission is needed.
- Settings (`ReadAloudScreen`): speed, pitch, maximum length, language when unknown, voice per language, and a preview. The preview is spoken by the engine itself, from the visible screen. The app bar's button plays the voice of the language when unknown, each language row its own voice, and each line of the voice picker that voice without closing the picker. The words are the engine's example sentence for the language, the one Android's text-to-speech settings play: `MainActivity` starts the default engine's `TextToSpeech.Engine.ACTION_GET_SAMPLE_TEXT` activity for a result over `tf/tts` (the manifest declares the intent in `<queries>`), and the screen keeps the answer per language and country. Without one it speaks the app's own sentence, in the language where the app has it and in the interface language otherwise.

## 8. Android platform notes

- **Foreground service** via `flutter_foreground_task`, service type `specialUse` with `PROPERTY_SPECIAL_USE_FGS_SUBTYPE` describing the persistent Telegram connection. `dataSync` is not usable: Android 15 and later cap it at 6 hours per day. The plugin does not declare the service, so the app manifest declares it with the type and the property. The service shows a permanent "Watching N channels" notification with a Pause action (the pause of section 6.2), which says "Paused: rules are not evaluated" with Resume while it holds.
- **Background watching** (`service.background`, device-local, not synced) is read by `CoreHost._connect` when the core is brought up. Off keeps the service from starting at all and stops one Android restored on boot, and the UI spawns the core in-process. The stop also holds for later boots, because the plugin's `RebootReceiver` skips `autoRunOnBoot` for a service stopped deliberately. The setting applies at the next app start, because the core cannot move between the service and the app while TDLib runs. Changing it offers "Restart now" (`AppHost.restart`): the host stops the service, or shuts the in-process core down, so TDLib is closed; then `tf/app.restart` starts `RestartActivity` in its own process (`:restart`), which kills the app's process and launches the app, and the new start settles where the core runs. Without the service there is no Telegram connection once the device dozes.
- **The service notification** sits on channel `core` at `LOW`. Android raises a foreground service's channel to `IMPORTANCE_LOW` whatever the app asks for, so no lower importance exists. How a `LOW` notification looks depends on the phone: stock Android puts it in the Silent section without a status-bar icon; Samsung's One UI shows it among the others, with its icon. The user can turn the `core` channel off in Android's settings; the service stays in the foreground and watching goes on, with nothing in the shade or the status bar. The last row of Notifications and sounds (`SystemNotificationSettingsRow`) opens Android's notification settings of the app (`tf/notifications.openAppSettings`, `ACTION_APP_NOTIFICATION_SETTINGS`), where every channel, `core` included, is turned off or changed.
- **Core isolate.** The foreground task runs a Dart callback in its own Flutter engine (`CoreServiceHandler`, the service host). It spawns the core isolate and registers the core's `SendPort` with `IsolateNameServer` under `telegram_feed.core`. The UI engine looks the port up on start and talks over it; both engines run in the same process, so ports work across them.
- **The core isolate is never respawned**, because each isolate would start its own `td_receive` loop. After a logout TDLib closes its client (`AuthClosed`); the core isolate creates a new client and gateway and `CoreServer.replaceGateway` swaps it in behind the same port, so UI clients see the new auth states.
- **Handing TDLib over.** Android restores the foreground service by itself when the process comes back, before Dart runs (`TaskStarter.system`), so the app can find a service core running after a kill. Stopping the service does not take that core down: its `td_receive` pump isolate keeps polling, and a second pump aborts the process ("Receive must not be called simultaneously from two different threads"). A core therefore hands TDLib back on the protocol's `shutdown` call: it closes TDLib's client and waits for `authorizationStateClosed`, so the database lock is free, then kills the receive isolate and waits for its exit (`FfiTransport.stopReceiving`). The service's `onDestroy` waits for `onStart` to finish, shuts its core down, and only then takes the port out of `IsolateNameServer`. `CoreHost` waits for that mapping to disappear, and asks any core still registered to stand down, before spawning its own.
- **The app's own channels in the service.** `MainActivity` registers the `tf/*` channels on the UI's engine only. The service's engine gets `tf/readAloudKeys` from `FeedApplication`, which registers a `FlutterForegroundTaskLifecycleListener` that installs it on every engine the service creates (`onEngineCreate`) and disposes of it with the engine; the application, not an activity, because Android starts the service without one after a reboot or an update.
- **Plugins with platform-to-Dart callbacks** (`flutter_tts`, `flutter_local_notifications`) cannot run in the core isolate: Flutter routes platform messages to the root isolate only. The service host owns them; the core sends it match events over the port. Callback-free method-channel calls (for example `path_provider`) work from the core isolate through `BackgroundIsolateBinaryMessenger`.
- **Battery.** Without an exemption from battery optimization Android kills the service after a while. The rules screen shows a banner asking for it until it is granted; the banner checks again when the app resumes and after the system dialog closes.
- **TDLib binaries.** `libtdjson.so` for `arm64-v8a` and `x86_64`, built in Docker (`tool/tdlib`, TDLib's own `example/android` build: NDK 23.2, static OpenSSL and libc++) from the commit pinned in `packages/tdlib_bindings/schema/TDLIB_COMMIT` (TDLib 1.8.67). TDLib has no git tags after v1.8.0, so the pin is a commit. The binaries have 16 KB LOAD alignment. `.github/workflows/tdlib.yml` publishes them as the release `tdlib-<sha7>`; `tool/fetch_tdlib.dart` downloads them into `jniLibs`. They are not committed.
- **Platforms.** Android only. iOS has no persistent foreground service, so on-device rule notifications cannot be delivered in real time there. There is no web build.

## 9. Several accounts

`AccountStore` keeps `accounts.json` in the support directory, outside every per-account database, since it says which of them to open. It holds the accounts (`AccountInfo`: id, name, phone, the path of a copy of the profile photo, the count of channels with unread posts, and `loggedIn`) and the one in use, at most four. Its changes read the file first and run one at a time. `AccountStore.tdlibOf`, `dbOf` and `photoOf` derive the account's TDLib directory, app database and photo copy from its id, and `appPaths([accountId])` uses them; account 1 uses `tdlib/` and `app.sqlite`. Both hosts call `appPaths()` without an id and so open the active account.

Switching restarts the host and its core instead of running a second core: the root (`main.dart`) calls `AppHost.standDown`, which closes the core client, the database and sync and then takes the core down (the service is stopped, or the in-process core asked to stand down), since the core is the old account's TDLib and database and a new host would attach to it if it lived on. Then a fresh host starts on the active account's paths; everything under `MaterialApp` rebuilds. `StatusBannerHost` takes the new host's notifiers in `didUpdateWidget` and puts its banner up again. An account without a session shows the login screen. `AccountSwitch` sits in `MaterialApp.builder`, above the navigator, so Settings, a pushed route, can reach it. Removing an account deletes its TDLib directory, its database file and its photo copy. The last account cannot be removed.

Only the account in use has a core, so what the list shows of the others is what was written while each was in use. `AccountRecord` (`host/account_record.dart`) stands around the home screen, which exists only under `AuthReady`: it marks the account as logged in before it asks Telegram for anything, then writes the profile from `me()` with a copy of the small profile photo (`AccountRecorder.profile`; the photo's own file lies in that account's TDLib directory), and the count of channels with unread posts whenever `HomeScreen.onUnreadChannels` reports another one. `AccountRows` lists every account but the one in use: photo or initials, name, phone, `UnreadBadge`; a tap switches, a long press removes after a question, and "Add an account" shows while there is room.

`AccountStore.add` writes the new account with `loggedIn: false`. `dropNeverLoggedIn` removes every such account that is not the one in use, with its data; it runs when the login screens' `OtherAccountButton` has gone back to another account (after the switch, when the abandoned account's core no longer holds its files) and when `AccountRows` loads. An entry without `loggedIn` (a file of an older build) is never dropped. `logOutAndWipe` clears the account's entry and sets `loggedIn: false` (`AccountRecorder.loggedOut`).

## 10. Privacy and security

- **Protected content.** `Post.canBeSaved` is TDLib's `message.can_be_saved`; a row is protected when any of its posts is (`TimelineItem.isProtected`). `PostCard` leaves Copy text, Share and Save out of such a post's menu and adds the official app's line about it, a block of code has no copy button, a selection that holds such a post has no Copy, Share or Save, and the viewer (`ViewerDetail.protected`) has no Share and neither save. `SecureWindow` (`host/secure_window.dart`) keeps Android's `FLAG_SECURE` on the window while anything holds it: the app lock while a PIN is set, a timeline while a protected post is loaded in it, and the viewer while it shows a protected picture.
- **App lock** (`settings/app_lock.dart`): a code that is a four-digit PIN or a password (`LockKind`, `lock.kind`; `AppLock.kindOf` tells them apart, and a code of an older build, whose kind was not kept, shows its kind the first time it unlocks), kept as a salted SHA-256 hash in the keystore (`LockStore`, the same storage as the AI key), and, where the user allows it, the device's fingerprint or face through `local_auth`, with the PIN always available. The lock is the device's: the keystore also holds its timeout, the fingerprint switch, the count of wrong PINs and the time the next try may be made, so it is on while a PIN exists, for every account, and a logout does not remove it (`AppLock.adoptLegacy` takes the timeout and the fingerprint switch over from the database of an older build). `LockGate` sits in the app's builder above the navigator and above the host, so no screen and no notification tap goes round it and a change of account keeps it as it is; it locks at every start of the process and when the app has rested longer than the timeout (at once, one minute, five minutes, one hour, five hours; one hour until changed), and when `LockButton` in the home screen's header counts `AppLock.lockNow` up. `LockScreen` draws `PinDots` and `PinPad` for a PIN and checks it with its fourth digit; a password, and a code whose kind is not known yet, are typed in a field and sent. From the third wrong PIN in a row the next try waits 5, 10, 15, 20, 25 and then 30 seconds (`AppLock.delayAfter`), counted down on the lock screen; a wrong PIN gets a new text field, because the keyboard keeps the digits of a field that was only cleared. While a PIN exists the window has `FLAG_SECURE` (`tf/app.secure`, `AppLock.applyToWindow`): the task switcher shows a blank card and screenshots are refused, unless "Show app content in task switcher" is on. The lock's own settings ask for the PIN first.
- The TDLib database and files are in the app's private storage. They are not encrypted: `database_encryption_key` is empty, and the app lock does not change that.
- Nothing leaves the device except Telegram traffic, with two exceptions the user turns on: Google Drive sync (section 5.5) stores feeds, rules and some settings in the user's own Drive, in a folder only this app can read; AI semantic rules (section 6.4) send the text of the posts they check to the endpoint the user configured.
- No analytics and no crash reporting.
- Logout turns sync off, deletes the AI key, wipes the app database and logs out of TDLib, which deletes its database and files directory.
- The manifest declares `INTERNET`, `POST_NOTIFICATIONS`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_SPECIAL_USE`, `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`, `WAKE_LOCK` and `VIBRATE`; plugins add their own (`local_auth` adds `USE_BIOMETRIC`).
- TDLib is built from pinned sources in Docker (`tool/tdlib`), never downloaded prebuilt from third parties.

## 11. Testing

- `rules`: unit tests for the parser and evaluator, including Unicode word boundaries, Cyrillic case folding and schedules that wrap past midnight.
- `core`: timeline merge, search, filters, rule engine and sync merge, tested against a fake `TelegramGateway` with scripted histories and update streams.
- `telegram_gateway`: tested against a scripted fake transport.
- `app_db`: a migration test for every schema version, against the dumps in `drift_schemas/`.
- `fake_telegram`: the scripted gateway every widget test reads from (`ChannelsGateway`: channels and folders; `TimelineGateway`: histories that page, search, live post events, `arrive` for a post that comes in now and `arrivedUnseen` for one that came in while the app was down), the fixture channels and posts, and `FakeTelegram`, a whole account: a login that takes any number and the code `12345`, three news channels in the folder "News", the "Wire" channel in the folder "Alerts" with a post arriving every 30 seconds, an archived channel, Saved Messages, posts of every kind, channel rows that carry their newest post in Telegram's order (the channel that posted last first; one is verified, one muted), a discussion thread, and media served from a directory. No test needs a real account, channel or post.
- The fake account has a "Media lab" channel (a video of 3:20, one of 40 seconds, a round video message, two songs, two voice messages) only while its files are in the fake's media directory. `tool/lab_media.sh` makes them with ffmpeg in Docker and pushes them to the emulator; they are not bundled, so tests and the UI flows, which start from cleared data, see the account without that channel.
- `app`: `app/test/fixtures.dart` re-exports `fake_telegram` and adds the pump helpers and the feed helper that needs the database.
- `app`: where a feed opens is tested in `app/test/feed_positioning_test.dart`: every read state (nothing read, read to a point, read through, one channel of two unread, one read position shared by two feeds, a channel timeline), reading that moves Telegram's read positions, the last post reading every channel of the feed, the button going to the divider, back to a tapped reply and to the end, the position kept across a restart and forgotten at the newest post, the app resting in the background and coming back without moving the reader, posts arriving while it rested or while the reader reads, and posts that came in while the app was down. The database is a file there, so closing and reopening it is a restart of the app.
- `app`: golden tests for the main screens (`tool/update_goldens.sh` regenerates them on Linux in Docker).
- The fake build, `--dart-define=TG_FAKE=true`: `CoreBootstrap.fakeMediaDirectory` is set, and the core isolate (in the service and in the app alike) serves a `FakeTelegram` instead of `TdlibGateway`; a logout makes a fresh one, so the login screens come back. At start the app copies `app/assets/fake/` (four pictures, a ten-second video, a text file, three avatars) into `<support>/fake/`, where the fake's downloads point. Everything else — the service, the rule engine, notifications, read-aloud, the database, every screen — is the real thing.
- `app/integration_test`: runs the real app on an emulator against the fake build: logs in, builds a feed and reads it.
- `app/maestro`: Maestro flows against the fake build, one per area (login, home, feed, search, media, feed editor, feed filter, rules, settings). Every flow starts from a cleared app and logs in; `subflows/` holds the shared pieces. `subflows/launch_clean.yaml` clears and launches the app and waits for the login screen; when it does not come, it launches again without stopping the app, because on a slow emulator Android can kill the app it has just launched while it still removes the cleared instance's task. A post that a flow taps or long-presses is scrolled to the middle of the screen first: where it lands depends on the time of day the fixture dates follow, and a sliver at the list's edge counts as visible but does not take the tap. `tool/maestro.sh` builds, installs and runs them on the connected emulator; the `ui` job of `ci.yml` does the same on a GitHub-hosted emulator. Before the flows it runs `tool/settle_emulator.sh`, which closes the "Pixel Launcher isn't responding" dialog a fresh emulator can show after boot (the runner presses a key before the launcher has a window) and which would otherwise cover every flow. When a flow fails there, `tool/ui_diagnostics.sh` prints the app's process, the focused window, the texts on screen, Android's records of apps that stopped responding or were killed (with the newest not-responding stack trace) and the app's log lines into the step log.
- Manual testing runs on Android emulators with x86_64 system images, never on personal devices. Telegram's test-DC test numbers (`99966XYYYY`) no longer work: Telegram disabled them ([tdlib/td#3083](https://github.com/tdlib/td/issues/3083)). The emulator therefore logs in with a spare real account on the production DC; the owner of that account types the phone number and code, and the TDLib session is reused between runs.
- `tool/ci.sh` runs what CI runs on the plain runner: analyze, format check, package tests and app tests.
